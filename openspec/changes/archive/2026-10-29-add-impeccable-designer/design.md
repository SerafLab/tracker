# Design

## Context

См. proposal.md. Приложение использует React/Vite, общие стили и существующие семантические элементы управления. Действующие требования application-shell и project-boards уже описывают доступность, локализацию, действия и порядок карточек. Названия, важность и срочность — текущие данные карточки; заметки и даты относятся к roadmap и не должны появляться в вариантах как реализованные возможности.

## Goals / Non-Goals

**Goals:** воспроизводимая роль дизайнера и два сравнимых работающих визуальных прототипа на существующих функциях. Минимальный рабочий контекст и явное разделение ответственности за дизайн и интеграцию.

**Non-Goals:** выбор направления за пользователя, замена рабочего UI до выбора, изменение данных, установка глобального инструментария, автоматические хуки, новый UI framework.

## Decisions

1. **Проектный upstream-пакет.** Impeccable поставляется в `.agents/skills/impeccable` из закреплённого commit вместе с лицензией и provenance. Это воспроизводимее глобальной установки. Сохраняем upstream инструкции; ограничения проекта задаём отдельно. Метаданные скилла отключают неявный запуск.
2. **Роль и контракт.** `.codex/agents/designer.toml` содержит имя, описание и инструкции, `docs/agents/designer.md` — поддерживаемый контракт. Маршрутизация разрешает запуск только по явному запросу пользователя. Два вспомогательных навыка передаются из каталога сессии, без пользовательских абсолютных путей в репозитории.
3. **Честная граница изоляции.** В интерфейсах с custom agents настройки уменьшают автозагрузку навыков. Текущий `collaboration.spawn_agent` не принимает custom agent/skills, поэтому используется `fork_turns: none` и явно переданные инструкции. Это поведенческое ограничение набора скиллов, не техническая изоляция файлов/инструментов. Модель/effort наследуются, если интерфейс не поддерживает предусмотренную правилами модель.
4. **Изолированные интерактивные варианты.** Оба направления находятся в `docs/design/board-directions`, используют одинаковые вымышленные данные и не читают хранилище приложения. Прототипы не подключены к production entry. На 320/390 и 1280/1440 px проверяются композиция, длинные имена, основные действия, клавиатура и переполнение; PNG подтверждают фактический вид. Разница в вариантах должна включать композицию или плотность, а не только цвет.
5. **Выбор перед продуктовыми изменениями.** Основной чат показывает варианты и получает выбор. Только после этого начинается отдельное изменение реализации выбранного UI. До выбора `PRODUCT.md` фиксирует факты о продукте, а ни один прототип не объявляется утверждённым `DESIGN.md`.
6. **Одна область настройки.** Это одна связанная задача в `codex/design-agent-impeccable`, base `d98d471a840afe6c272974d1a2445d7800cc023b`. Setup-исполнитель владеет `.agents`, `.codex`, `docs/agents`; дизайнер — `docs/design/board-directions` и `PRODUCT.md`; координатор — OpenSpec, проверками и интеграцией. Пересечения авторов отсутствуют. Полный npm check выполняется координатором.

## Risks / Trade-offs

- Большой upstream-пакет → фиксировать версию, читать только необходимые references, не устанавливать автоматические hooks.
- Инструкции выглядят как техническая изоляция → в контракте явно различать native configuration и проверенный fallback текущей сессии.
- Красивый макет скрывает потерю функций → одинаковый набор данных и действий, проверка относительно текущих спецификаций; демо не доказывает сохранность production-данных.
- Прототип принимают за выпуск → явная подпись демонстрационных данных и отдельное сообщение о статусе настройки и последующего редизайна.

## Migration Plan

Данные и production-приложение не мигрируют. После проверки и reviewer настройки и прототипы могут быть доставлены одним PR по обычным правилам репозитория; это не утверждение визуального направления. Откат — revert коммита настройки без изменения пользовательских данных. Upstream runtime-кэш остаётся вне репозитория.
