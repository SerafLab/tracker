# Design

## Context

См. [proposal.md](proposal.md). Карточки и статусы хранятся в IndexedDB отдельными таблицами с порядковыми позициями; внешних ключей и каскадного удаления нет. Мутации проходят через repository, use cases и store, а UI обновляется после успешного сохранения. `ActionMenu` и `ActionDialog` уже используются для вторичных действий. Параллельное изменение `unify-app-bar` меняет оболочку и содержимое диалогов, поэтому новый диалог должен работать с итоговым общим компонентом.

## Goals / Non-Goals

**Goals:**

- Сохранить существующий поток подтверждённой мутации: сначала атомарная запись, затем обновление доски.
- Сохранить целостность связей и плотный порядок после удаления.
- Дать различимые результаты для запрещённого удаления непустого статуса и сбоя хранилища.
- Сохранить доступность меню и управления фокусом при открытии, отмене и подтверждении диалога.

**Non-Goals:**

- Миграция схемы IndexedDB: новых полей и таблиц нет.
- Механизм восстановления удалённых объектов.

## Decisions

### 1. Удалять объект и уплотнять позиции в одной транзакции

`deleteCard(id)` читает карточку и все карточки её статуса, удаляет выбранную и записывает оставшиеся с позициями `0…n-1` в одной транзакции. `deleteStatus(id)` в одной транзакции проверяет существование карточек данного статуса, удаляет только пустой статус и уплотняет позиции остальных статусов проекта. Проверка пустоты внутри транзакции нужна, чтобы карточка не появилась между проверкой и удалением. Удаление по ID сохраняет корректность при совпадающих названиях. Для статуса транзакция включает таблицы статусов и карточек.

Альтернатива: удалять отдельно и перенумеровывать позднее. Она допускает промежуточные нарушения порядка и частичное сохранение при сбое.

### 2. Возвращать отказ из-за карточек отдельно от ошибки записи

Repository сообщает о непустом статусе отдельной доменной ошибкой или типизированным результатом; use case и store переводят его в отдельный результат для UI. Ошибки записи продолжают устанавливать `saveError`, оставляя прежнее подтверждённое состояние доски. Отказ из-за карточек не должен выглядеть как сбой хранилища. После успешного удаления store перечитывает открытую доску. Результат удаления используется для вызова `onMutationSaved` только при успешной записи.

Альтернатива: обрабатывать все исключения как `saveError`. Тогда пользователь получит неверную причину отказа.

### 3. Использовать общее подтверждение удаления из меню объекта

Добавить действие удаления в меню карточки и статуса. Общий диалог называет конкретный объект, предупреждает о необратимости и содержит явные кнопки отмены и удаления. Для статуса, который уже содержит карточки, показать в диалоге объяснение и путь решения, не выполнять удаление; повторить проверку в repository на случай изменения данных после открытия диалога. При ошибке записи оставить диалог и объект доступными для повторной попытки. Строки добавить для русского и английского языков.

Альтернатива: использовать системный `window.confirm`. Он хуже согласуется с существующими диалогами, не позволяет ясно показать причину запрета и усложняет управление фокусом.

### 4. Явно управлять фокусом при удалении

При открытии диалога фокусировать безопасную кнопку отмены. При отмене возвращать фокус на меню соответствующего объекта. После успешного удаления вернуть фокус на существующий элемент того же контекста: ближайшую карточку или меню статуса для карточки, соседний статус или кнопку добавления статуса для статуса. Не пытаться фокусировать удалённый пункт меню. Проверить клавиатуру и узкий экран. Общее поведение `ActionDialog` согласовать с изменением `unify-app-bar`, где переключатель языка убирается из диалогов.

Альтернатива: положиться на автоматическое восстановление фокуса существующего диалога. При удалении объекта его исходный элемент размонтируется.

## Risks / Trade-offs

- [Два окна приложения могут менять одну доску] → Проверять наличие карточек в той же транзакции, которая удаляет статус, и показывать отдельный отказ.
- [Активное `unify-app-bar` меняет общую разметку диалога] → Интегрировать подтверждение поверх итогового `ActionDialog` и проверить взаимодействие изменений перед реализацией общего UI.
- [После удаления последнего статуса меняется компоновка доски] → Использовать уже существующее пустое состояние и проверить доступность создания нового статуса.

## Migration Plan

Миграция данных не нужна. Новые операции работают с текущими таблицами. При откате к предыдущей версии приложения ранее удалённые данные не восстанавливаются; оставшаяся структура данных читается прежней версией.
