# card-details Specification

## Purpose

Позволяет открыть карточку и сохранить её подробности и историю личных заметок, чтобы продолжать дело с нужными сведениями и договорённостями.

## Requirements

### Requirement: Whole-card detail navigation
Система SHALL открывать отдельную страницу карточки обычным нажатием на её свободную площадь и семантическим контролом с клавиатуры. Меню и его действия SHALL работать самостоятельно. Начатое перетаскивание, его завершение или отмена и жест прокрутки SHALL не открывать страницу карточки.

#### Scenario: User clicks the card body
- **WHEN** пользователь обычно нажимает на название, метку или свободную площадь карточки без перетаскивания и прокрутки
- **THEN** открывается страница именно этой карточки

#### Scenario: User operates card controls
- **WHEN** пользователь нажимает верхнее меню карточки или пункт меню
- **THEN** нажатие не начинает перетаскивание и не открывает страницу вследствие всплытия; выбранное действие выполняет только свою операцию

#### Scenario: Keyboard user opens details
- **WHEN** пользователь фокусирует семантический контроль открытия карточки и нажимает Enter
- **THEN** открывается её страница, а фокус перемещается в основной контент

#### Scenario: User chooses editing from the menu
- **WHEN** пользователь выбирает «Редактировать» в меню карточки
- **THEN** открывается та же страница карточки с сохранёнными основными полями

#### Scenario: User releases a dragged card
- **WHEN** пользователь завершает либо отменяет начатый жест переноса, в том числе без изменения позиции или вне допустимой цели
- **THEN** связанное с жестом отпускание и последующий синтетический клик не открывают карточку, а следующий самостоятельный обычный клик открывает её

#### Scenario: User scrolls from a card
- **WHEN** пользователь прокручивает доску или страницу свайпом, начатым на свободной площади карточки
- **THEN** страница карточки не открывается и последующий самостоятельный обычный тап сохраняет возможность открытия

### Requirement: Addressable card page and board return
Страница карточки SHALL иметь собственный адрес, открываться напрямую и после перезагрузки и предоставлять возврат к своей доске. Система SHALL проверять принадлежность карточки проекту и явно обрабатывать отсутствие карточки или проекта.

#### Scenario: User follows a direct address
- **WHEN** пользователь открывает адрес существующей карточки или перезагружает его
- **THEN** отображаются её подтверждённые поля и заметки в контексте соответствующего проекта

#### Scenario: User returns to the board
- **WHEN** пользователь выбирает «Назад к доске» на странице карточки, в том числе открытой напрямую
- **THEN** после разрешения несохранённых изменений открывается родительская доска с актуальными карточками

#### Scenario: Requested card is unavailable
- **WHEN** адрес ссылается на отсутствующую карточку или карточку другого проекта
- **THEN** чужие данные не показываются и доступно понятное сообщение с переходом на указанную существующую доску

#### Scenario: Requested project is unavailable
- **WHEN** проект в адресе отсутствует
- **THEN** приложение переходит к каталогу без показа карточки другого проекта

### Requirement: Card description and explicit field saving
Страница SHALL показывать название, необязательное описание, важность и срочность и сохранять эти поля вместе кнопкой «Сохранить». Описание SHALL поддерживать многострочный текст и очистку до пустого значения. Сохранение основных полей SHALL не закрывать страницу и не терять черновик заметки.

#### Scenario: User saves all basic fields
- **WHEN** пользователь меняет название, описание и признаки и выбирает «Сохранить»
- **THEN** все поля сохраняются вместе, страница остаётся открытой, название в заголовке обновляется

#### Scenario: User clears the description
- **WHEN** пользователь очищает описание и успешно сохраняет
- **THEN** описание остаётся пустым после перезагрузки без изменения заметок

#### Scenario: User changes description without changing flags
- **WHEN** пользователь сохраняет только новое описание
- **THEN** порядок карточки внутри своей группы не меняется

### Requirement: Dated personal note history
Страница SHALL показывать отдельные заметки карточки с датами создания и позволять добавить непустую заметку самостоятельным действием. Заметки SHALL отображаться от старых к новым в стабильном порядке; даты SHALL соответствовать языку интерфейса и локальному часовому поясу. Создание заметки SHALL не сохранять и не сбрасывать черновики основных полей.

#### Scenario: User adds a note
- **WHEN** пользователь вводит многострочный текст и выбирает «Добавить заметку»
- **THEN** после сохранения заметка с датой появляется в истории, очищается только её поле ввода, страница остаётся открытой

#### Scenario: User submits an empty note
- **WHEN** пользователь отправляет пустой или состоящий из пробелов текст заметки
- **THEN** заметка не создаётся, форма показывает ошибку и остаётся доступной

#### Scenario: Card has no notes
- **WHEN** пользователь открывает карточку без заметок
- **THEN** история показывает понятное пустое состояние и доступно добавление первой заметки

### Requirement: Editable and confirmed deletable notes
Система SHALL позволять исправить заметку отдельным сохранением и удалить её только после подтверждения, идентифицирующего запись. Изменение SHALL сохранять исходную дату и позицию и показывать отметку «изменено»; сохранение прежнего текста SHALL не создавать отметку. Отмена SHALL сохранять запись.

#### Scenario: User edits an existing note
- **WHEN** пользователь сохраняет изменённый непустой текст заметки
- **THEN** текст обновляется с отметкой изменения, исходной датой и прежним местом в истории

#### Scenario: User saves an unchanged note
- **WHEN** пользователь сохраняет текст без фактических изменений
- **THEN** дата изменения и отметка изменения не добавляются и не обновляются

#### Scenario: User confirms note deletion
- **WHEN** пользователь подтверждает удаление выбранной заметки
- **THEN** удаляется только эта заметка, результат сохраняется после перезагрузки, фокус остаётся на доступном контроле истории

#### Scenario: User cancels note deletion
- **WHEN** пользователь отменяет подтверждение удаления
- **THEN** заметка остаётся без изменений

### Requirement: Plain text with usable web links
Описание и заметки SHALL сохранять многострочный обычный текст и показывать абсолютные HTTP/HTTPS ссылки как кликабельные. HTML и Markdown SHALL отображаться как текст. Открытие веб-ссылки SHALL сохранять страницу карточки и её черновики.

#### Scenario: User views multiline text and a URL
- **WHEN** сохранённый текст содержит переносы строк и абсолютную HTTPS ссылку
- **THEN** переносы сохраняются, ссылка доступна мышью и клавиатурой и открывается отдельно от карточки

#### Scenario: User saves markup or another URL scheme
- **WHEN** пользователь сохраняет HTML, Markdown или адрес javascript/data
- **THEN** содержимое не исполняется как разметка или код и опасный адрес не становится активной ссылкой

### Requirement: Guarded navigation with unsaved drafts
При несохранённых основных полях или черновике новой/редактируемой заметки система SHALL перед внутренним переходом, Back/Forward или управляемым обновлением приложения предлагать сохранить и выйти, выйти без сохранения или остаться. Переход после сохранения SHALL происходить только при успехе всех ожидающих сохранений.

#### Scenario: User leaves after saving drafts
- **WHEN** пользователь выбирает «Сохранить и выйти», а основные поля и заметка корректны и записаны
- **THEN** применяется исходно выбранный переход без повторного подтверждения и без дублирования заметки

#### Scenario: User discards pending changes
- **WHEN** пользователь выбирает «Выйти без сохранения»
- **THEN** только оставшиеся черновики отбрасываются и выбранный переход выполняется

#### Scenario: User remains on the page
- **WHEN** пользователь выбирает «Остаться», закрывает диалог или нажимает Escape
- **THEN** страница, значения черновиков и текущая запись навигации сохраняются

#### Scenario: Saving only partly succeeds
- **WHEN** при «Сохранить и выйти» основные поля записаны, но сохранить заметку не удалось
- **THEN** переход не выполняется, поля остаются подтверждёнными, текст заметки остаётся черновиком с ошибкой и доступной повторной попыткой без дубликатов

#### Scenario: User switches note editors
- **WHEN** пользователь начинает другую заметку при несохранённом тексте текущей
- **THEN** текущий черновик защищён тем же выбором перед переключением

#### Scenario: User reloads or closes the browser
- **WHEN** пользователь пытается нативно перезагрузить страницу или закрыть вкладку с черновиком
- **THEN** приложение запрашивает стандартное браузерное предупреждение, если браузер его поддерживает, без обещания сохранения при закрытии

#### Scenario: User activates an app update
- **WHEN** пользователь выбирает обновление приложения при наличии черновиков
- **THEN** управляемая активация и перезагрузка ждут решения guard; отмена или ошибка сохранения оставляет текущую страницу

### Requirement: Local durable note operations and failures
Описание, заметки и их даты SHALL сохраняться локально, работать офлайн и не меняться при переносе карточки. При ошибке операции заметки подтверждённые данные SHALL оставаться прежними, введённое SHALL сохраняться для повторной попытки и успех SHALL не объявляться.

#### Scenario: User returns offline
- **WHEN** пользователь сохраняет описание и заметки, повторно открывает установленное приложение без сети
- **THEN** сохранённые данные доступны и новые локальные изменения можно сохранить

#### Scenario: User moves a detailed card
- **WHEN** пользователь переносит карточку в другой статус
- **THEN** описание, заметки и даты сохраняются у той же карточки

#### Scenario: A note operation fails
- **WHEN** создание, изменение или удаление заметки не удаётся записать
- **THEN** история остаётся в последнем подтверждённом состоянии, редактор/подтверждение остаётся доступным с введённым текстом и сообщением об ошибке

### Requirement: Accessible localized detail page
Страница и диалоги SHALL быть доступны с клавиатуры и на ширине 320 px, иметь подписанные поля, видимый фокус и русские/английские подписи и ошибки. Длинные тексты и ссылки SHALL не перекрывать действия и не создавать горизонтального переполнения страницы. Пользовательский текст SHALL не переводиться.

#### Scenario: User works on a narrow screen in English
- **WHEN** пользователь открывает карточку с длинными текстами при английском интерфейсе на ширине 320 px
- **THEN** поля, история, ссылки, даты и действия доступны и читаемы без горизонтального scroll страницы, подписи и ошибки английские

#### Scenario: User interacts with confirmation using a keyboard
- **WHEN** пользователь открывает подтверждение удаления или ухода с черновиком
- **THEN** фокус входит в диалог и остаётся внутри него, а отмена возвращает его к вызвавшему действию
