# Design

## Context

Мотивация и согласованный объём описаны в `proposal.md`. Текущий порт `ProjectBoardRepository` поддерживает удаление карточек и только пустых статусов; проект удалить нельзя. Dexie хранит проекты, статусы, карточки и предпочтение `lastProjectId` в отдельных таблицах. Zustand обновляет подтверждённое состояние после записи. Hash-навигация и восстановление последнего проекта находятся в `src/app/app.tsx`.

`ProjectCatalogueView` имеет меню переименования; на доске переименование находится в общем AppBar. `DeleteDialog` и `ActionDialog` уже обеспечивают подтверждение, отмену, повторную попытку и управление фокусом. Тест `deletion.test.tsx` явно проверяет отсутствие удаления проектов — это ожидание требуется заменить.

Дизайн нужен, поскольку операция затрагивает транзакцию нескольких таблиц, состояние, навигацию и общий интерфейс.

## Goals / Non-Goals

**Goals:** единый путь удаления из двух экранов, атомарное сохранение и независимая обработка последующего обновления экрана, согласованный маршрут и фокус.

**Non-Goals:** универсальный механизм удаления сущностей, новая схема хранения, MCP-инструмент удаления, новая система диалогов. Существующий запрет удаления непустого статуса остаётся: удаление всего проекта является отдельной операцией.

## Decisions

### 1. Один метод репозитория с транзакцией каскада

Добавить `deleteProject(id): Promise<void>` в порт и use cases. В Dexie выполнить одну read-write транзакцию по `projects`, `statuses`, `cards`, `workspace`: проверить существование проекта, получить его статусы по `projectId`, удалить карточки этих статусов, статусы и проект; очистить `lastProjectId`, только если он равен удаляемому ID. Данные читать внутри транзакции, а не использовать снимок доски из диалога. При отсутствии проекта завершить безопасно без затрагивания других данных (повторное удаление не требует специального восстановления).

Вызовы существующих `deleteStatus` последовательно непригодны: они запрещают непустые статусы и не обеспечивают общий откат. Оптимистическое скрытие также не подходит, поскольку интерфейс должен отражать подтверждённую запись. Новая версия базы для текущих таблиц не требуется.

### 2. Отделить commit от навигации

Store возвращает результат записи, не скрывает проект до commit и соблюдает существующий `canMutate`. Ошибка транзакции выставляет ошибку сохранения, оставляет workspace и подтверждение без изменений. После commit обновить каталог и сообщить об успешной мутации существующему `onMutationSaved`.

При удалении с доски на уровне приложения очистить hash и показать каталог. Не использовать повторную запись `clearLastProject` как обязательное условие перехода: нужное предпочтение уже очищено атомарно репозиторием. Иначе удаление могло бы сохраниться, а переход ошибочно зависел бы от второй записи. При удалении из каталога обновить только список. Существующий обработчик отсутствующего проекта использовать для старых ссылок/истории.

Если обновление каталога после успешного commit не удалось, показать существующее состояние недоступности; не выдавать это за отказ транзакции и не предлагать повторить уже сохранённое удаление. Восстановление после перезагрузки читает фактически сохранённое состояние.

### 3. Переиспользовать подтверждение и общий AppBar

Расширить `DeleteDialog` вариантом проекта и сводкой количества статусов/карточек, сохранив текущие правила карточек/статусов. Каталог перед открытием подтверждения загружает выбранную доску через существующий query use case, не вызывая `showBoard` и не меняя маршрут/последний проект. Пока сводка загружается или загрузка не удалась, подтверждать удаление нельзя; показать загрузку/ошибку и дать повторить чтение или отменить. На доске брать сводку из её актуального состояния.

Расширить AppBar явным необязательным действием удаления проекта; передать его только с доски. Это оставляет каталог и служебные экраны с языковыми настройками. Обе точки входа используют одинаковые переводы, предупреждение, начальный фокус на отмене и блокировку повторной отправки.

Количество в подтверждении — снимок для пользователя; каскад всегда охватывает актуальное содержимое проекта на момент транзакции. Не вводить подписки между вкладками в рамках этой функции.

### 4. Явно назначать фокус после удаления

Отмена возвращает фокус к trigger меню проекта или шестерёнке. После удаления в каталоге выбрать следующий проект по прежнему порядку, иначе предыдущий, иначе создание проекта. После удаления с доски фокусировать создание проекта в каталоге. Передавать цель фокуса через состояние представления/контейнера и применять после монтирования, чтобы размонтированный trigger не забирал фокус.

### 5. Учесть параллельные изменения без расширения объёма

`add-agent-mcp-integration` исключает удаление проектов из инструментов; общий порт может расшириться без изменения MCP-discovery. `add-card-details` затрагивает AppBar, маршруты, карточки и планирует отдельные заметки: при интеграции использовать актуальные контракты, а уже существующие дочерние заметки удалять в той же транзакции. Если заметки добавятся позднее, их изменение должно расширить все каскады. Эти предложения не редактируются данной работой.

## Risks / Trade-offs

- [Удаление необратимо] → название, количества, явное предупреждение и безопасный начальный фокус; корзина не предусмотрена по согласованному решению.
- [Частичное удаление или зависшее предпочтение] → одна транзакция и тест отката после промежуточного удаления.
- [Маршрут остаётся на удалённой доске] → переход после commit, проверки перезагрузки и истории браузера.
- [Ошибка чтения принимается за ошибку записи] → разделить результат транзакции и последующее обновление экрана.
- [Пересечения с будущими заметками и MCP] → согласовать актуальные таблицы и контракты при совместном внедрении, проверить отсутствие потерянных дочерних данных.
- [Содержимое меняется в другой вкладке после открытия диалога] → сводка является снимком; транзакция читает актуальные связи и не оставляет карточки без проекта.

## Migration Plan

Изменения текущей схемы и миграция данных не нужны. Внедрить порт/репозиторий, затем состояние и UI, выполнить проверки. Перед готовым PR синхронизировать delta-specs и архивировать изменение в той же ветке. Откат кода не восстанавливает уже удалённые данные; данные других проектов не преобразуются.
