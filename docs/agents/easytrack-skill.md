# Навык EasyTrack для внутреннего браузера

Репозиторный навык находится в [`.agents/skills/easytrack/`](../../.agents/skills/easytrack/SKILL.md). Он учит агента выбирать вкладку EasyTrack, работать с карточками через native WebMCP и показывать доску. Навык не устанавливает сервер, не переносит данные и сам по себе не подтверждает готовность опубликованных инструментов. Статус фактической интеграции и её приёмки см. в [руководстве WebMCP](mcp-integration.md) и [записи браузерной проверки](mcp-browser-qa.md).

## Подключение в текущем и другом чате

1. В Codex откройте этот репозиторий как рабочую папку. Навык размещён в стандартном репозиторном каталоге `.agents/skills/` и может вызываться как `$easytrack`. Если изменение не появилось в списке навыков, перезапустите Codex.
2. Для локального чата с другой рабочей папкой перенесите **всю папку** `easytrack`, включая `references/` и `agents/`, в `.agents/skills/` выбранного проекта. Альтернативный пользовательский каталог для доступа из разных локальных проектов — `~/.agents/skills/easytrack`. Перед копированием проверьте, что навык с таким именем уже не установлен; существующую папку не перезаписывайте автоматически. Эти действия здесь не выполняются: репозиторий не меняет глобальную конфигурацию или пользовательские навыки.
3. В выбранном чате должен быть доступен внутренний браузер, умеющий управлять вкладками и вызывать native WebMCP инструмент выбранного документа. Обычный stdio MCP-клиент этим условием не является. Skill не добавляет отсутствующую браузерную возможность и не обещает работу в любом чате.
4. Попросите агента: «Используй `$easytrack`, открой мои проекты». Он откроет или переиспользует обычный адрес `https://seraflab.github.io/tracker/`, получит фактически зарегистрированные инструменты и проверит `get_connection`, версию контракта и готовность. При отсутствии возможностей или task-инструментов агент сообщает конкретное ограничение.

Модель выбранного чата тоже должна поддерживать Site tools. В реальной проверке gpt-5.6-luna отклонила webmcp_list_tools; смена модели пользователем позволила продолжить. [Официальная документация OpenAI](https://learn.chatgpt.com/docs/changelog?date=2026-09-03&index=2) указывает GPT-5.6 Sol/Terra и исключает GPT-5.6 Luna. Это не повод менять origin, включать другой транспорт или переписывать данные.

Пути локального обнаружения и обновление списка навыков описаны в [официальной документации OpenAI](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills). Установка инструкций не даёт новых разрешений браузера и не добавляет MCP/relay в пользовательские настройки.

Вкладка и локальные данные остаются в выбранном браузерном контексте. Проект из обычного Chrome, другого внутреннего браузера или установленной PWA не переносится в него автоматически. Не меняйте браузер и не создавайте проект заново только потому, что другой контекст показывает пустой каталог.

## Примеры запросов

- «Используй `$easytrack`: покажи проекты и статусы проекта “Поиск квартиры”».
- «Добавь карточку “Позвонить владельцу” в статус “Связаться” проекта “Поиск квартиры”. Она важная, но не срочная».
- «Перенеси эту карточку в “Просмотр” и покажи доску».
- «Удали карточку “Тест навыка” из указанного проекта» — только если это действительно намерение пользователя; при совпадении названий сначала выбирается конкретный ID.

Создание проекта через агента принимает только название и создаёт пустую доску. Карточки получают пустое описание; инструмент обновления меняет название и признаки, сохраняя описание. Заметки, описание, наборы статусов и удаление проекта не редактируются этим API. Перенос добавляет карточку в конец её группы важности/срочности. Обычный интерфейс сохраняет собственные доступные операции.

При несохранённых полях или заметке конфликтующее действие и показ другого экрана отказываются с `conflict`. Агент не стирает черновик и не закрывает его принудительно. При потере ответа после возможной записи результат неизвестен: сначала нужно прочитать фактическую доску, затем отдельно решить, требуется ли новая попытка. Одинаковые названия не доказывают, что запись не произошла.

## Пользовательский walkthrough нового чата

Этот walkthrough требует пользователя и выполненного выпуска task-интеграции. Фактическая приёмка записана в [core QA](webmcp-core-qa.md); сама инструкция не является доказательством её прохождения. Пользователь открывает новый чат сам либо отдельно явно просит агента создать его; запрос на реализацию функции такого разрешения не даёт.

В поддерживаемом внутреннем браузере и на отдельно разрешённых тестовых данных:

1. Закройте тестовую вкладку EasyTrack. В новом чате вызовите `$easytrack` и попросите показать проекты. Проверьте, что агент открывает обычный опубликованный URL и называет фактически обнаруженную сессию готовой только после ответа приложения.
2. Попросите добавить одну явно тестовую карточку в существующие проект и статус. Проверьте в доске сохранённое название, признаки и порядок. Если проекта/статуса несколько, агент должен уточнить цель, а не создать новую молча.
3. Попросите «покажи задачи». Сначала должен завершиться `show_workspace`, затем должна стать видимой та же вкладка с соответствующей доской. Черновик должен вызвать отказ перехода, сохранив ввод.
4. Если host поддерживает неотображаемую панель браузера, выполните один разрешённый тестовый вызов в таком режиме и снова покажите доску. Зафиксируйте отдельно видимость панели и документа: это не проверка выгруженной или закрытой страницы.
5. Перезагрузите/повторно откройте ту же вкладку и проверьте сохранность карточки и новую привязку сессии. Явно разрешённое удаление тестовой карточки должно выбрать её ID и сохранить платформенное подтверждение, если host его запрашивает.

Запишите URL/версию приложения, host и браузер, выбранный контекст, обнаруженные инструменты, результаты сохранения/показа/повторного открытия и ограничения видимости. Не включайте личное содержимое карточек в отчёт. Статусы «инструкция проверена», «кандидат проверен», «опубликовано» и «walkthrough нового чата пройден» различаются.

## Контроль инструкций без живых изменений

Следующие сценарии предназначены для независимой проверки поведения skill. Они не доказывают работоспособность core или production native API:

| Исходная ситуация | Ожидаемое решение агента |
| --- | --- |
| Два проекта с одинаковым названием | Получить ID и уточнить выбор; без создания проекта/статуса |
| Пользователь хочет переместить карточку, но не удалять | Не вызывать destructive tools и не отправлять `confirm:true` |
| Явно удаляется выбранная карточка | Только её ID, свежая сессия/ID запроса, `confirm:true`; платформенное подтверждение сохраняется |
| Host добавил суффиксы к именам | Вызвать только точное имя из свежей discovery выбранной вкладки |
| Документ перезагрузился, старый handle ещё известен | Fresh discovery и `get_connection`; старая сессия не используется |
| После создания host выбросил исключение, на доске две одинаковые записи | Неизвестный исход; read-only проверка, без автоматической третьей записи и без приписывания конкретного ID потерянному вызову |
| Старый requestId вышел из bounded journal | Не обходить high-water новым повторным ID; сначала проверить состояние и решение пользователя |
| `show_workspace` вернул `conflict` из-за черновика | Не сообщать об успешном переходе и не открывать другой контекст |
| Есть браузер, но native discovery отсутствует | Сообщить ограничение; без DOM CRUD, внешнего браузера, stdio или другой origin |
| Панель не показана, документ сообщил `visible` | Сообщить именно unshown-panel execution, не поддержку hidden/closed document |
