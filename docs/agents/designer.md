# Дизайнер интерфейса

Дизайнер подключается только по явному запросу пользователя. Новый экран или
изменение UI само по себе не разрешает его запуск. Основной чат сохраняет
ответственность за требования, продуктовые решения, общение, интеграцию,
проверки и доставку. Дизайнер отвечает за визуальное решение и его реализацию
в назначенной области; он не запускает других субагентов.

## Контекст и скиллы

Конфигурация роли: [designer.toml](../../.codex/agents/designer.toml).
Модель не закреплена: используется модель среды; ограничения выбора модели
и усилия основной чат сообщает в постановке задачи.

- Основной скилл: глобальный `impeccable` (`~/.codex/skills/impeccable`; для Claude
  Code — симлинк `~/.claude/skills/impeccable`). Ссылки на команды и материалы
  читаются по мере необходимости.
- `web-design-guidelines` — при проверке интерфейса.
- `vercel-react-best-practices` — при реализации React.

Основной чат передаёт реальные пути всех трёх скиллов из каталога текущей сессии.
Пользовательские абсолютные пути не записываются в репозиторий. Если скилл отсутствует, дизайнер сообщает об этом основному чату; не подменяет
его инструкциями, которых не читал.

В конфигурации отключены bundled skills и автоматическая вставка инструкций
скиллов. Impeccable имеет `policy.allow_implicit_invocation: false` для Codex
и `disable-model-invocation: true` для Claude Code. Это уменьшает
автоматически загружаемый контекст, но не создаёт технический список разрешённых
из трёх скиллов и не ограничивает доступ к файлам или инструментам.

## Запуск из основного чата

Если интерфейс поддерживает выбор пользовательского агента, выбрать `designer`
из `.codex/agents/designer.toml`, сверившись с возможностями текущей среды.
Схема: [официальная документация Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents).

В текущем `collaboration.spawn_agent` нет параметров выбора пользовательского
агента или набора скиллов. `task_name: "designer"` только даёт имя задаче и не
применяет TOML. Доступный способ — отдельный контекст с `fork_turns: "none"` и
полной постановкой: прочитать `designer.toml` как инструкции роли и этот документ,
явно использовать выбранные скиллы. При таком запуске поля `[skills]` из TOML
не применяются. Основной чат сообщает, что ограничение скиллов здесь поведенческое.

В постановку включить:

- явный запрос пользователя и этап: варианты, реализация выбранного варианта или проверка;
- путь рабочего дерева, ветку, базовый коммит и разрешённые файлы;
- текущие требования, ссылки на продуктовые документы и применимые спецификации;
- два пути вспомогательных скиллов и доступные средства просмотра в браузере;
- исходный экран, данные для сравнения и область выборочной визуальной проверки: экраны, размеры, языки и состояния, относящиеся к изменению;
- подтверждённый выбор пользователя, если поручается реализация.

## Рабочий процесс

Первое применение — редизайн доски и app bar в режиме Impeccable `Operate`.
Сохранить продуктовые факты, функции и пользовательские сценарии. Можно менять
композицию, типографику, цвета и отступы. Продуктовые вопросы передавать основному
чату. Существующий внешний вид служит исходным состоянием, а не обязательным
визуальным ограничением при согласованном редизайне.

1. Изучить реальный интерфейс, требования и существующие правила. Использовать
   [продуктовые документы](../product/vision.md) и актуальную реализацию как
   источники фактов для `PRODUCT.md`; не выдумывать недостающие сведения.
2. Подготовить два заметно разных визуальных направления на одинаковом содержимом.
   Показать доску и app bar в обоих вариантах, объяснить композицию и компромиссы.
   Проверить прототипы в браузере. До выбора пользователя не менять рабочий UI.
3. Основной чат представляет варианты и получает выбор. Ответ на другой вопрос,
   отсутствие ответа или прошедшее время не считаются выбором.
4. Реализовать выбранный вариант в назначенной области. Перед UI-правками читать
   `reference/craft-floor.md`. Проверить затронутый отрисованный интерфейс в браузере
   по [правилу выборочного просмотра скриншотов](rules/visual-review.md).
   Выбрать применимые пункты [визуальной проверки](../manual-visual-qa.md): узкую
   ширину, длинные названия, переполнение, пустые состояния и клавиатуру, если они
   затронуты. Явные критерии приёмки выполнить в заданной области; всю матрицу
   скриншотов после каждого прогона не просматривать.
5. Передать основному чату изменённые файлы, фактически просмотренные экраны,
   размеры, языки и состояния, результаты, визуальные материалы и существенные
   ограничения. Основной чат может использовать этот отчёт без повторного открытия
   тех же снимков, показывает результат пользователю и организует интеграцию
   и обязательные проверки. Успешные тесты не заменяют визуальный просмотр.
6. После принятия результата закрепить решения в существующих правилах дизайна
   проекта или `DESIGN.md`, опираясь на реализованный интерфейс. Невыбранные
   прототипы не становятся стандартом проекта.

Последующие задачи сохраняют явный запуск; количество вариантов и область работы
определяются новым запросом. Уже утверждённые решения не требуют повторного выбора
при обычной реализации в рамках принятого направления.

## Launcher и границы установки

Impeccable установлен глобально, вне репозитория; версия, лицензия и локальные
адаптации записаны в `PROVENANCE.md` рядом со скиллом. Если скилла нет в среде,
дизайнер сообщает об этом основному чату. Hooks и глобальные настройки
Impeccable не устанавливаются. Не запускать `install`, `update`,
`link`, `hooks`, `pin` или настройку live-watch как побочный эффект дизайн-задачи.
Встроенные upstream роли сохранены для целостности пакета, но дизайнер не получает
разрешения запускать их: проект запрещает субагентам создавать субагентов.

Upstream launcher проверяет скачиваемый движок по SHA256 из пакета. Для его кэша
можно задать `IMPECCABLE_HOME` на временный каталог, например
`IMPECCABLE_HOME=/tmp/traker-impeccable-runtime`, без изменения `$HOME`.
Проверка `engine-probe` не устанавливает hooks. `context` запускается один раз
за сессию с cwd проекта, как указано в скилле. При недоступном движке использовать
документированный в `SKILL.md` fallback: сообщить основному чату, затем читать
имеющийся продуктовый и дизайн-контекст напрямую. Ошибка launcher не разрешает
подменять визуальную проверку заявлением об успешном запуске.
