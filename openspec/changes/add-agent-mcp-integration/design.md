# Design

## Context

См. `proposal.md` для мотивации. EasyTrack — статическое React/Vite-приложение на `https://seraflab.github.io/tracker/`. `src/app/app.tsx` собирает Dexie repository, use cases и Zustand store в одном браузерном runtime. Данные изолированы по браузерному storage context. Маршрут доски — `#project/<id>`.

`application/use-cases.ts` уже предоставляет нужные операции. Store обновляет экран после действий UI, но многие его методы переключают отображаемую доску. Repository допускает no-op для некоторых отсутствующих ID. Браузерный адаптер должен устранить эти неоднозначности, не дублируя правила приоритета и проектной изоляции.

## Goals / Non-Goals

**Goals:**
- MCP-контракт зависит от операций продукта, а не от Dexie или будущей базы.
- Одна открытая сессия исполняет типизированные команды в том же runtime, что и интерфейс.
- Показ приложения использует средства внутреннего браузера агента; запись не зависит от DOM.

**Non-Goals:**
- Нет серверного хранения задач, облака, смены origin, доступа к файлам браузерного профиля, общего eval или нового CRUD для несуществующих возможностей продукта.
- Нет гарантии работы при закрытой/выгруженной вкладке, гарантии exactly-once после перезапуска процесса или синхронизации разных браузеров.

## Decisions

### 1. stdio MCP и отдельный браузерный транспорт

Локальный Node.js-процесс обслуживает MCP через stdio официальным SDK. Тот же процесс слушает WebSocket только на `127.0.0.1` со случайным свободным портом. Опубликованный EasyTrack подключается к нему исходящим соединением. MCP-процесс держит только транспортную сессию, pending requests и ограниченный временный журнал ответов; задач на диск не записывает. Логи идут в stderr и не содержат pairing secrets или содержимого карточек.

Использовать актуальный поддерживаемый официальный TypeScript SDK, совместимую schema library и поддерживаемую WebSocket-библиотеку; закрепить версии при реализации. Не реализовывать MCP wire protocol вручную. Node-зависимости не включать в браузерный bundle.

Альтернативы: SQLite/HTTP backend отвергнуты пользователем; автоматизация форм отвергнута пользователем; browser extension/CDP создают дополнительную зависимость от управления профилем и не выбраны.

### 2. Обязательная проверка целевого браузера до основной реализации

Первый implementation gate проверяет с production HTTPS origin во внутреннем браузере Codex: соединение с loopback WebSocket, доступность браузерного разрешения, исполнение в фоновой вкладке, сохранение того же storage context при повторном открытии. Это не доказано нынешними localhost Playwright-тестами и не проверялось при подготовке предложения.

[Chrome Local Network Access](https://developer.chrome.com/docs/modern-web-guidance/guides/security/local-network-access) описывает отдельные разрешения для loopback и особенности WebSocket. Из этого не следует поддержка конкретным IAB. Зафиксировать версию приложения/движка, путь permission prompt и фактический результат. Не отключать защиту браузера. Если gate не проходит, остановить зависящую реализацию и пересмотреть транспорт с пользователем; нельзя незаметно заменить браузер, origin или хранилище.

### 3. Pairing и жизненный цикл

Служебные MCP tools: `get_connection` возвращает состояние и при необходимости одноразовую connection URL; `disconnect` отзывает сессию. URL использует существующий HTTPS origin и отдельный bootstrap fragment с портом и криптографически случайным токеном. Bootstrap разбирается до обычного hash routing, token немедленно удаляется через replaceState и хранится только в памяти вкладки. Не помещать secret в query, логи, localStorage или примеры документации. После перезагрузки повторить pairing; не сохранять постоянный доступ автоматически.

Relay проверяет точный разрешённый Origin, допустимый Host, аутентификацию первым сообщением, версию протокола и схему каждого сообщения; не принимает команды до аутентификации. Browser adapter принимает только loopback endpoint и перечисленные команды. Другие origin допускаются лишь явно в тестовой конфигурации. Origin не заменяет токен и сам по себе не изолирует соседние сайты того же origin.

Одна pairing-сессия допускает одного исполнителя. Повторный клиент не вытесняет его. Разрыв помечает соединение disconnected; новое pairing явно выбирает вкладку. Закрытие/перезапуск процесса отзывает все токены. Ограничить время handshake, размер сообщений, число pending calls и время ответа. React effects корректно отключают bridge при cleanup и выдерживают StrictMode.

### 4. Контракт инструментов

| Tool | Вход | Результат |
| --- | --- | --- |
| `list_projects` | нет | проекты с ID, именем и датой создания |
| `get_board` | projectId | проект, упорядоченные статусы и карточки |
| `create_project` / `rename_project` | name / projectId, name | сохранённый проект |
| `create_status` / `rename_status` | projectId, name / statusId, name | сохранённый статус |
| `move_status` | statusId, direction: left/right | обновлённая доска |
| `delete_status` | statusId, confirm: true | удалённый ID либо status_not_empty |
| `create_card` | statusId, name, important=false, urgent=false | сохранённая карточка |
| `update_card` | cardId, name, important, urgent | сохранённая карточка |
| `move_card` | cardId, statusId | сохранённая карточка |
| `delete_card` | cardId, confirm: true | удалённый ID |
| `show_workspace` | необязательный projectId | route и канонический app URL |

`show_workspace` меняет маршрут через приложение; видимость вкладки обеспечивает агент через browser tool. Частичное обновление карточек, поиск с отдельным индексом и batch endpoint не нужны: для текущего объёма агент читает доску и передаёт полные поля. Неоднозначные имена разрешаются чтением ID; при нескольких подходящих вариантах skill спрашивает пользователя. Не создавать статусы и проекты молча.

Успешный результат содержит `ok`, сохранённый `data` и session ID. Ошибки используют MCP error result и структурированный code: invalid_argument, not_found, conflict, status_not_empty, storage_unavailable, restart_required, disconnected, incompatible, outcome_unknown. Инструменты имеют read-only/destructive annotations; destructive calls требуют `confirm: true` и явно выраженного намерения пользователя в skill. Этот параметр не является техническим доказательством согласия человека. Существующие UI-подтверждения удаления остаются.

### 5. Исполнение в браузере и согласование экрана

Браузерный command adapter получает зависимости через composition root после открытия storage. Он вызывает use cases через публичный API feature, не импортирует Dexie и не пишет таблицы напрямую. Проверки существования и принадлежности выполняются в application/repository boundary; устранить успешные no-op для отсутствующих целей, а проверки мутаций выполнить в соответствующей транзакции, чтобы не было check-then-write race.

Использовать общий mutation guard для UI и MCP: stale IndexedDB connection запрещает запись обоим. Bridge сериализует свои команды, но UI может работать параллельно; окончательные ограничения проверяются на записи. Успех определяется commit, не успешностью последующей перерисовки. После commit перечитать текущий catalogue/board без смены маршрута и вызвать существующий callback запроса persistent storage, где применимо. Если refresh не удался, результат сообщает `saved: true` и отдельное предупреждение о представлении; повторять мутацию нельзя.

Явный `show_workspace` использует существующую навигацию. Не применять напрямую store-методы, которые переключают доску при фоновых изменениях другого проекта. Проверить согласование preferred project: `create_project` сейчас сохраняет lastProjectId, но фоновая операция не должна неожиданно менять текущий маршрут.

### 6. Потеря результата и повторные вызовы

Каждое transport request получает session-scoped request ID. Browser adapter хранит ограниченный журнал выполняющихся/завершённых ID до разрыва сессии; повтор того же ID не исполняет мутацию заново. Не обещать dedup для нового MCP вызова с новым ID или после reload. Не держать команды в offline queue.

Если dispatch не состоялся, вернуть disconnected. Если dispatch состоялся, но подтверждение потеряно, вернуть outcome_unknown; отмена ожидания не означает rollback. Не повторять автоматически. Skill сначала читает актуальную доску и сверяет результат; для одинаковых карточек нельзя утверждать, что конкретная запись точно создана потерянным вызовом. Нужна новая явная попытка с учётом фактического состояния.

### 7. Агентный workflow

Репозиторный skill объясняет: проверить connection, переиспользовать известную вкладку или открыть bootstrap URL внутри IAB, дождаться ready, разрешить project/status ID и вызвать MCP. Если host не поддерживает скрытую вкладку, открыть обычную внутреннюю вкладку и сообщить ограничение. Не применять shell browser opener или DOM automation для CRUD. Для показа вызвать `show_workspace`, затем сделать вкладку видимой. Permission prompt, который host не может обработать, передаётся пользователю как конкретное препятствие.

Документировать регистрацию MCP и установку skill для использования в чатах вне репозитория; не изменять глобальную конфигурацию пользователя автоматически. Отсутствие зарегистрированного MCP не выдавать за работающее подключение. Проверить фактическое обнаружение инструментов новым чатом при приёмке. Создание skill при реализации следует поручить `skill-creator`.

## Risks / Trade-offs

- IAB может блокировать loopback или выгружать фоновые вкладки → первый gate, bounded timeouts и честное disconnected; никакой подмены данных.
- Потеря ответа после commit → outcome_unknown и запрет replay; persistent exactly-once journal не добавляется.
- Новое приложение в другом origin показывает пустую базу → сохранять текущий GitHub Pages origin и выбранный storage context.
- Разделённые мутации и refresh могут конкурировать с UI → транзакционные инварианты и перечитывание подтверждённого состояния.
- Секрет pairing доступен странице → короткая сессия, memory-only token, allowlist команд; произвольный код не принимается.
- MCP не подключён к конкретному чату → инструкция регистрации и проверка реальным клиентом, без обещания универсального доступа.

## Migration Plan

1. Пройти IAB transport gate в изолированном эксперименте; записать evidence. Основные работы зависят от результата.
2. Внедрить контракты, application adapter, relay и browser bootstrap; существующая схема IndexedDB не меняется.
3. Добавить skill, настройку запуска, документацию и проверки; интеграция по умолчанию не подключается без pairing.
4. Выполнить `npm run check`, MCP client tests и реальный сценарий в IAB. Обновить продуктовые границы и ADR в рамках реализации, синхронизировать спецификации и архивировать change перед готовым PR.
5. Опубликовать app через обычный main/Pages процесс, настроить MCP и skill по инструкции и проверить production сценарий. При откате отключить relay и вернуть версию интеграции; IndexedDB не мигрировала и данные доступны обычному приложению.

## Open Questions

Нет отложенных продуктовых решений. Конкретные версия SDK, свободный порт и численные лимиты уточняются при реализации без изменения контракта. Совместимость IAB остаётся технически непроверенной и является первым gate, а не подтверждённой возможностью.
