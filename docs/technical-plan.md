# Технический план веб-MVP

Статус: технический план веб-MVP согласован 6 октября 2026 года. Реализация и настройка публикации ещё не начаты.

## Исходные требования

- Автор имеет почти десять лет опыта с React и TypeScript. Учебная цель проекта — пройти полный цикл разработки с AI и OpenSpec.
- Первый выпуск — личное веб-приложение с локальными данными, повторным открытием без интернета и ручной резервной копией. Полные границы описаны в [vision.md](product/vision.md).
- Использование с телефона обязательно. Поддерживаются актуальный Chrome на компьютере, реальных iPhone и Android, а также Safari на реальном iPhone. Минимальные исторические версии пока не обещаются; для каждого выпуска записываются фактически проверенные версии ОС и браузеров.
- Установленное веб-приложение входит в основной мобильный сценарий и критерии офлайн-проверки.
- Первый MVP публикуется из публичного репозитория `SerafLab/tracker` на GitHub Pages по постоянному адресу `https://seraflab.github.io/tracker/`.
- Аккаунты, автоматическая синхронизация и совместная работа относятся к последующим этапам.

## Согласованная основа

Приложение — статическое клиентское SPA на React и TypeScript в строгом режиме. Vite используется для локальной разработки и production-сборки. Серверная часть для веб-MVP отсутствует. Hash-навигацией владеет `src/app/app.tsx` согласно ADR-0004: каталог, `#project/<projectId>` и `#project/<projectId>/card/<cardId>`. Индексированные записи history защищают черновики при Back/Forward; устаревшие чтения не заменяют новый экран. Подтверждённый snapshot хранит Zustand, черновики редакторов — React. React Router для этих маршрутов не используется.

Проект использует npm и коммитит `package-lock.json`. Среда разработки и CI работают на Node.js 24 LTS; major-версия фиксируется в `.nvmrc`, `package.json#engines` и GitHub Actions. При создании приложения выбираются актуальные совместимые стабильные версии зависимостей, а точный граф фиксируется lockfile.

Интерфейс оформляется через CSS Modules и небольшой набор глобальных design tokens. Tailwind, CSS-in-JS и UI-kit в MVP не используются. Основные действия строятся на семантических HTML-элементах. Перемещение карточки доступно через верхнее меню: выбор другого статуса добавляет в конец собственной группы, шаги «Поднять выше» и «Опустить ниже» меняют порядок только среди карточек с теми же признаками. Drag-and-drop — дополнительный способ: современный `@dnd-kit/react` предоставляет PointerSensor, feedback и AutoScroller. До активации разрешена нативная прокрутка обеих осей; мышь активирует перенос после 5 px, touch — после удержания 250 ms с допуском 5 px. Ранний sensor gate подтверждён пользователем на Chrome iPhone/Android и Safari iPhone, итоговая физическая приёмка ведётся отдельно в QA. Ссылка сохраняет обычные tap/click/Enter; меню остаётся доступным без жестов. Горизонтальный autoscroll ограничен доской, вертикальный использует реальный scroll ancestor. На время drag отключается scroll-snap, чтобы он не отменял шаги AutoScroller; preview не изменяет подтверждённый snapshot.

GitHub Pages используется для публикации, GitHub Actions — для автоматической сборки, проверок и публикации. Pages раздаёт статические файлы, а логика и пользовательские данные остаются в браузере. При добавлении аккаунтов и синхронизации архитектура будет пересмотрена.

GitHub Pages предоставляет HTTPS. Для выбранного проектного адреса Vite собирается с `base: "/tracker/"`; тот же базовый путь учитывается в ресурсах, навигации и области действия service worker. Переезд на другой origin не входит в MVP, потому что браузерное хранилище автоматически вместе с приложением не переносится.

Решение и его ограничения зафиксированы в [ADR-0001](adr/0001-static-local-first-github-pages.md). Деплой ещё не настроен.

## Данные и работа без интернета

Пользовательские данные хранятся в IndexedDB через Dexie. Для проектов, статусов, карточек и заметок используются отдельные нормализованные хранилища; карточка содержит название, описание и независимые признаки важности/срочности. Заметка принадлежит карточке и содержит текст, дату создания и необязательную дату изменения. Сущности получают UUID, порядок статусов и карточек хранится явно. React обращается не к Dexie напрямую, а к репозиторному слою с доменными операциями и транзакционными границами.

Размещение использует единый `CardPlacement`: целевой `statusId`, `beforeCardId: Id | null` и `expected` с исходными `statusId`, `important`, `urgent`. Anchor означает вставку перед peer своей группы после исключения переносимой карточки, `null` — конец собственной группы. Репозиторий в одной транзакции повторно читает источник/статусы/списки, проверяет проект, ожидаемые поля и anchor, затем перенумеровывает затронутые списки. Неверный или устаревший anchor отклоняется; неизменившийся порядок не записывается. Сохраняются ID, описание, заметки и даты; новая миграция не нужна. Board-level guard блокирует конфликтующие мутации на время commit/refresh. После отказа записи виден подтверждённый snapshot; после успешного commit с ошибкой refresh разрешено повторить только чтение, без повторного переноса. Клавиатурное перемещение возвращает фокус на меню карточки по ID с `preventScroll`, pointer drag не добавляет программной прокрутки.

Текущая схема Dexie v3 добавляет notes (`id, cardId, [cardId+createdAt]`) и заполняет пустое описание существующих карточек. Создание/правка заметки проверяют связи внутри транзакции, история отсортирована по дате создания и ID. Удаление карточки атомарно удаляет её заметки и перенумеровывает остальные карточки; перенос сохраняет описание, заметки и их даты. Схема IndexedDB версионируется средствами Dexie. Миграции выполняются только вперёд и транзакционно; автоматические потенциально разрушающие миграции в MVP запрещены. Откат опубликованных файлов приложения безопасен только до изменения схемы данных. После миграции используется исправляющий выпуск либо восстановление совместимой резервной копии; downgrade базы не поддерживается.

Резервная копия — версионированный JSON-файл с временем экспорта и всеми пользовательскими данными. Zod проверяет структуру и поддерживаемую версию файла до записи в базу. Перед восстановлением приложение показывает краткий состав копии и запрашивает подтверждение, после чего атомарно заменяет текущие данные одной транзакцией. Объединение с существующими данными не входит в MVP. Повреждённый файл или файл из неподдерживаемой будущей версии отклоняется без изменения базы.

Для повторного открытия без интернета `vite-plugin-pwa` и Workbox в режиме `generateSW` создают service worker. В precache входят app shell и локальные файлы production-сборки: HTML, JavaScript, CSS, web app manifest, иконки и необходимые локальные шрифты. Навигационный fallback и область действия ограничены базовым путём `/tracker/`. Состав сгенерированного precache и ограничения размера файлов проверяются по артефакту сборки.

Runtime-кеширование внешних страниц, сторонних ресурсов и API не используется. Сохранённые ссылки могут требовать сеть, API в MVP отсутствует, а пользовательские данные принадлежат IndexedDB. Хранение данных и кеширование файлов приложения остаются независимыми задачами.

Новая сборка скачивается в фоне, но не активируется посреди работы. Приложение показывает предложение обновиться; после подтверждения и разрешения несохранённых черновиков активирует новый service worker и перезагружается. Для основных полей и активной заметки доступны сохранение и выход, выход без сохранения и отмена перехода. Сохранение при уходе последовательно: подтверждённые поля остаются записанными при ошибке заметки; повтор сохраняет только оставшуюся часть. Без сети продолжает работать последняя активированная версия. При событии `versionchange` старая вкладка закрывает соединение Dexie и предлагает перезапуск, чтобы старый код не продолжал работу с обновлённой схемой. Миграция базы начинается только после активации новой версии приложения.

Офлайн-критерий проверяется после первоначальной онлайн-загрузки: пользователь устанавливает веб-приложение, закрывает его, отключает сеть, снова запускает, читает и изменяет данные, затем ещё раз закрывает и открывает приложение и видит сохранённые изменения. Проверка выполняется на реальных iPhone и Android. Обычный запуск в Chrome на телефоне также проверяется; на iPhone дополнительно проверяется Safari.

В текущих границах данные отдельны для каждого браузера и устройства. Публикация одного адреса на Pages не синхронизирует их: карточка, добавленная на компьютере, автоматически на телефоне не появится. Автор подтвердил, что для MVP это приемлемо: синхронизация и авторизация пользователя не входят в первый выпуск.

Перенос на другой origin потребует отдельного плана переноса локальных данных. Решения по хранению, миграциям и резервной копии зафиксированы в [ADR-0002](adr/0002-indexeddb-and-versioned-backups.md), стратегия кеширования и обновлений — в [ADR-0003](adr/0003-generated-service-worker-and-prompted-updates.md).

## Путь от изменения до выпуска

1. Локально проверить изменение по его спецификации OpenSpec, выполнить `npm run check`, синхронизировать завершённые спецификации и архивировать изменение в рабочей ветке.
2. Агент коммитит результат, отправляет ветку и создаёт pull request в `main`.
3. Обязательные проверки pull request проходят в GitHub. После их успеха PR сливается методом squash: через GitHub auto-merge, если он включён в репозитории, либо самим агентом после проверки результата CI. Неуспешные проверки блокируют слияние.
4. Слияние запускает сборку, публикацию в GitHub Pages и автоматическую проверку опубликованного адреса. Проверка на реальных устройствах относится к оформлению именованного выпуска и не блокирует эту публикацию.

Базовые команды проекта:

- `npm ci` — воспроизводимая установка по lockfile;
- `npm run dev` — локальная разработка;
- `npm run build` и `npm run preview` — production-сборка и её локальная проверка;
- `npm run format:check`, `npm run lint`, `npm run typecheck` — форматирование, статический анализ и TypeScript;
- `npm test` — тесты Vitest и React Testing Library;
- `npm run test:e2e` — критические браузерные сценарии Playwright;
- `npm run check` — полный набор блокирующих проверок без ручной мобильной приёмки.

ESLint использует flat config, type-aware правила `typescript-eslint`, правила React Hooks и `eslint-plugin-jsx-a11y`; форматирование выполняет Prettier. Vitest проверяет доменную логику, миграции и преобразования резервной копии, React Testing Library — наблюдаемое поведение компонентов. Общий процент покрытия не блокирует изменение: тестами обязательно покрывается критическое поведение и найденные регрессии.

Playwright запускает критические пользовательские сценарии против production-сборки в Chromium и WebKit, включая мобильные размеры экрана и настоящую IndexedDB. Автоматизированная проверка service worker, офлайн-переключения и обновления выполняется в Chromium, поскольку расширенная поддержка service worker в Playwright ограничена Chromium. WebKit даёт дополнительный сигнал совместимости, но не заменяет выпускную проверку на реальном iPhone.

Отдельное preview-окружение и custom domain в MVP не используются.

### GitHub Actions и защита основной ветки

`ci.yml` запускается для pull request в `main`. Его уникально названные jobs выполняют статические проверки, тесты и production-сборку; они обязательны для merge. `deploy-pages.yml` запускается после push в `main`, повторяет блокирующие проверки для точного публикуемого коммита, собирает один каталог `dist`, загружает его как Pages artifact и публикует через environment `github-pages`.

Основная ветка защищена: изменения попадают в неё только через pull request с актуальной базой, успешной обязательной проверкой и закрытыми обсуждениями; force-push и удаление запрещены. Approving review и merge queue для единственного разработчика не требуются. Используются squash merge и линейная история. Настройка `Allow auto-merge` позволяет GitHub завершить слияние в фоне; если она выключена, агент выполняет слияние после проверок без дополнительного подтверждения.

Actions фиксируются полными commit SHA с комментарием версии. Dependabot еженедельно предлагает обновления npm-зависимостей и Actions. Обычные jobs получают только `contents: read`; только deploy job получает `pages: write` и `id-token: write`. Устаревшие CI-запуски одной ветки отменяются, а Pages deployments выполняются последовательно без прерывания уже начатой публикации.

### Deployment, release и восстановление

Каждый успешный merge в `main` автоматически публикуется. После deploy автоматический smoke проверяет выбранный URL, app shell, manifest и регистрацию service worker. Deployment становится именованным release после ручной приёмки на реальных iPhone и Android; успешный коммит получает тег `v0.x.y` и GitHub Release. Интерфейс показывает версию и короткий commit SHA, эти сведения также входят в резервную копию.

Полный мобильный checklist обязателен для первого выпуска и изменений хранилища, миграций, service worker или резервной копии. Для остальных изменений достаточно сокращённого smoke основного сценария на опубликованной версии. Для каждого release записываются фактически проверенные версии ОС и браузеров.

Для визуальных изменений доски используйте [план ручной визуальной проверки](manual-visual-qa.md): он задаёт viewport, набор состояний, проверку keyboard focus и шаблон записи результата.

Если схема базы не менялась, для восстановления можно повторно опубликовать предыдущий коммит. После миграции старый bundle не публикуется: применяется исправляющий выпуск вперёд либо восстановление совместимой резервной копии.

## Перед началом реализации и первым выпуском

- Определить первое небольшое изменение и описать его в `openspec/changes/`; планы не выдавать за реализованное поведение.
- При создании проекта записать точные версии выбранных зависимостей в `package-lock.json` и проверить их совместимость с Node.js 24 LTS.
- До первого release настроить защиту `main`, Pages, workflows, Dependabot и environment `github-pages`.
- На первом release записать фактические версии ОС, Chrome и Safari на основном iPhone и доступном Android-телефоне и пройти установленный офлайн-сценарий, сохранность данных, обновление и резервную копию.
- Существенные новые труднообратимые решения с реальными альтернативами фиксировать отдельными ADR.

## Document-bound native агентный доступ

Согласованная интеграция регистрирует 15 native WebMCP tools (контракт версии 2: create_project требует statusSetId, добавлен apply_status_set) в обычном документе через document.modelContext, при наличии API. Browser adapter в composition root импортирует только публичный index project-board; authoritative commands и shared UI/agent/DnD guard используют существующую IndexedDB schema3 без второй task DB. Zod генерирует native input schemas и валидирует inputs/results в browser runtime; динамический chunk не загружается обычным UI без native API, а PWA precache сохраняет его для offline reload. Node/stdio/relay transport и расширенный exposedTo отсутствуют в browser bundle; исторические диагностические scripts остаются отдельными.

Background create_project атомарно создаёт проект с выбранным набором статусов (none — без статусов) и remember:false, не восстанавливая preference второй записью. Attributes update_card сохраняет актуальное description внутри транзакции общей с UI priority logic. move_card использует точный CardPlacement с beforeCardId:null/expected и append собственной группы. Смонтированные fields/note drafts сохраняются при unrelated refresh и его ошибке; postcommit успех возвращается с отдельным warning и read-only recovery. show_workspace подтверждает реальный route и preference после await checked navigation, без void requestLeave как ложного доказательства перехода.

Сессия живёт в документе; pagehide/BFCache/reload отзывают прежний runtime, ledger64/high-water не переживает reload. Тайм-аут/abort ответа не снимает настоящий pending guard и не означает rollback записи. Общий store lease сохраняется через замену native runtime до фактического завершения операции. [ADR-0005](adr/0005-document-bound-native-agent-tools.md), [контракт и руководство](agents/mcp-integration.md), [отдельные стадии QA](agents/webmcp-core-qa.md) фиксируют ограничения hosts и обязательный последующий production/new-chat handoff.

## Card presentation and navigation

App owns the single card address and its browser-history presentation. Opening from the board pushes a panel entry; switching cards replaces that entry; expanding pushes a page entry with the same URL. Direct links, new tabs and reloads use the full page. A shared editor preserves drafts when expanding. The board main element remains the same vertical scroll container before, during and after the panel; opening a later card therefore retains its scroll position. On desktop the board stays mounted and interactive beside the independently scrolling panel; on narrow screens the panel covers the screen, traps keyboard focus, and all background workspace, installation and update controls are inert. Zustand stores confirmed board/card snapshots; successful writes refresh the board without resetting editor drafts. The React Router dependency does not own these routes.
