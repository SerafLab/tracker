# Design

## Context

Мотивация описана в `proposal.md`. Сейчас `CardInput` содержит название и два признака, Dexie использует схему v2, заметок нет. `CardDialog` обслуживает создание и редактирование. `Workspace` различает каталог и доску, а успешные мутации вызывают `showBoard`, поэтому прямое повторение этого подхода закроет будущую страницу карточки.

Hash-навигацией реально владеет `src/app/app.tsx`, как закреплено ADR-0004; React Router, упомянутый в раннем technical-plan, сейчас не используется. Представление и Zustand зависят от use cases, домена и порта репозитория; Dexie остаётся адаптером. Данные локальны для origin и браузера.

## Goals / Non-Goals

**Goals:** расширить существующий feature без второго источника данных, обеспечить транзакционные сохранения, понятные ошибки и управляемую навигацию с черновиками.

**Non-Goals:** общий редактор документов, история версий текста, инфраструктура совместной работы, рефакторинг всего приложения или поддержка прежних внутренних API. Остальные границы перечислены в proposal.

## Decisions

### 1. Страница и навигация остаются внутри текущих границ

Добавить маршрут `#project/<projectId>/card/<cardId>` и состояние страницы с подтверждёнными данными карточки, её проекта, статуса и заметок. Проверять принадлежность карточки проекту при чтении. Прямой адрес и перезагрузка открывают карточку; отсутствующая карточка показывает понятное состояние с возвратом на существующую доску, отсутствующий проект — переход к каталогу. Нельзя подставить карточку другого проекта.

Единый владелец навигации в app обрабатывает каталог, доску, карточку и pending destination, не добавляя отдельный роутер. Это меньше, чем внедрение React Router ради одного маршрута. Использовать записи history с известным индексом, чтобы перехватывать Back/Forward, восстанавливать текущую запись до решения пользователя и затем применять исходный переход один раз. Быстрые повторные переходы не создают несколько диалогов; устаревшие async-загрузки не заменяют более новый экран. «Назад к доске» имеет явный адрес родительской доски и работает после прямого открытия карточки.

### 2. Карточка целиком кликабельна без вложенных контролов

Сохранить `li` и самостоятельные стрелки/меню. Семантическая ссылка на страницу с доступным именем по названию карточки покрывает свободную площадь через CSS; остальные контролы — её siblings с самостоятельной областью нажатия. Не делать кнопку вокруг кнопок. Enter на ссылке открывает страницу, стрелки и пункты меню выполняют только свои действия, в том числе недоступные стрелки не превращаются в ссылку. Меню «Редактировать» открывает ту же страницу, отдельный edit-dialog удаляется.

### 3. Основные поля и заметки имеют разные контракты

`Card` получает обязательную строку `description`, пустую по умолчанию; `CardInput` — четыре редактируемых поля. Создание остаётся компактным диалогом с названием и двумя признаками; описание присваивается `''`, заполняется на странице. Это явный минимальный default, а не вторая форма подробного редактирования.

Новая сущность `Note`: `id`, `cardId`, `text`, `createdAt`, необязательный `updatedAt`. UUID и ISO UTC timestamps выдаёт use case через существующие зависимости `createId`/`now`; редактирование сохраняет `createdAt`, устанавливает `updatedAt` только при фактической правке. Пустой после trim текст не сохраняется, внутренние переносы и пробелы сохраняются. История идёт от старых записей к новым, при равном времени — по id; редактирование её не переставляет. Даты отображляются через `Intl.DateTimeFormat` в текущем языке и локальном часовом поясе пользователя. Это личные заметки, авторства и веток ответов нет.

Порт получает чтение деталей с проверкой проекта и операции create/update/delete note. Операции заметок проверяют существование карточки; правка/удаление проверяют принадлежность заметки этой карточке. Основные поля сохраняются одной транзакцией вместе с изменением priority order. Описание и заметки сами не меняют порядок. Удаление карточки, всех её заметок и перенумерация оставшихся карточек — одна транзакция. Перенос сохраняет описание и заметки без перепривязки.

### 4. Обновлять подтверждённые данные, сохраняя текущий экран

Zustand хранит подтверждённый snapshot, React — черновики и их исходные значения. Успешная мутация обновляет snapshot текущей карточки либо доску по контексту, а не безусловно вызывает `showBoard`. Ошибка оставляет snapshot прежним и сохраняет введённый текст. Обновление списка заметок не сбрасывает несохранённые основные поля и наоборот.

На странице одновременно открыт один редактор заметки: новый либо существующий. Переключение редактора при dirty проходит через тот же guard. Сохраняемые мутации защищены от повторной отправки. После добавления заметки очищается только её черновик; после правки закрывается её редактор. Удаление требует отдельного подтверждения с идентификацией записи и возвращает фокус к соседней записи или добавлению.

### 5. Защита черновиков имеет точную границу

Dirty сравнивает поля с последним подтверждённым snapshot и учитывает новый/изменённый текст заметки. App регистрирует у страницы обработчики проверки, сохранения и сброса. Переходы по «Назад», бренду, внутренним ссылкам, Back/Forward и управляемая кнопка обновления приложения сначала показывают один диалог: «Сохранить и выйти», «Выйти без сохранения», «Остаться». При отсутствии dirty переход немедленный.

Для «Сохранить и выйти» сначала сохранять основные поля, затем активный черновик заметки. Это последовательные самостоятельные операции, как и явные кнопки на странице. Если первая прошла, а вторая нет, основные поля уже подтверждены, их dirty сброшен; заметка остаётся черновиком, страница и pending destination не применяются, ошибка явно сообщает о несохранённой заметке. Повторная попытка не создаёт дубликат и не повторяет уже подтверждённую операцию. При валидационной ошибке переход также отменяется. «Выйти без сохранения» сбрасывает только оставшиеся черновики; «Остаться»/Escape ничего не теряют.

Для закрытия вкладки и нативной перезагрузки устанавливается `beforeunload` только при dirty: браузер сам показывает стандартное предупреждение, без обещания собственного диалога или сохранения при закрытии. Управляемое обновление PWA активирует worker/reload только после guard. Аварийное завершение процесса и forced restart после закрытия stale DB не гарантируют сохранение черновика; нельзя пытаться писать через закрытое соединение.

### 6. Обычный текст, общий shell и локализация

Использовать textarea, обычный React text rendering и `linkify-react` для распознавания только абсолютных HTTP/HTTPS URL в отображаемом описании и заметках; не интерпретировать HTML/Markdown и не использовать `dangerouslySetInnerHTML`. Веб-ссылки открываются отдельно с `noopener noreferrer`, чтобы не уводить страницу с черновиком. Адаптер и настройка URL описаны в [официальной документации React](https://linkify.js.org/docs/linkify-react.html) и [options](https://linkify.js.org/docs/options.html): фильтр HTTP/HTTPS, отключение email, target/rel. Выбор версии проверяется по актуальной совместимости при реализации; отдельный формат хранения не нужен. Альтернатива rich-text editor избыточна согласованному обычному тексту.

В AppBar — сохранённое название карточки как единственный h1, настройки языка и бренд с переходом к каталогу через guard. Возврат на доску явно доступен; создание статуса и переименование проекта на странице карточки не показываются. На 320 px длинный текст и ссылки переносятся, формы и история не создают горизонтального переполнения. Все подписи, ошибки, даты и confirmation RU/EN; пользовательский текст не переводится.

## Risks / Trade-offs

- Перехват hash history и повторные async-запросы могут терять маршрут → browser-тесты Back/Forward, прямого адреса, отмены и ошибки сохранения; один владелец переходов.
- Последовательное сохранение при уходе может завершиться частично → явный контракт подтверждённых частей и проверка повторной попытки без дублей.
- Будущий MCP change использует старый `CardInput` и обновление доски → перед совместной реализацией согласовать его контракты; не менять его артефакты или добавлять MCP в это изменение.
- Большой текст увеличивает страницу → обычный документный scroll и перенос ссылок; пагинация и лимиты не добавляются без измеренной необходимости.

## Migration Plan

1. Добавить схему Dexie v3 с `notes: 'id, cardId, [cardId+createdAt]'`; существующие stores/индексы сохранить. В upgrade атомарно присвоить карточкам `description: ''`, сохранив имена, связи, flags и position; notes первоначально пуст.
2. Проверить обновление реальных v1 (через существующую v2) и v2, повторное открытие, откат транзакции при ошибке и `versionchange` старой вкладки. Тест с искусственной newer v3 поднять выше новой актуальной версии.
3. Выпустить обычным PWA-путём с существующим предложением обновления. Не активировать обновление поверх dirty-редактора без решения пользователя.
4. При сбое upgrade транзакция откатывается и показывается ошибка хранилища. После успешного upgrade откат на старый исполняемый код не поддерживается: восстановление — исправляющий релиз с этой или следующей схемой, без удаления пользовательской базы.
