# Design

## Context

См. [proposal.md](proposal.md). Доска уже передаёт в `CardView` упорядоченные статусы, а `moveCard` в репозитории транзакционно меняет статус карточки, добавляет её в конец целевой колонки и уплотняет позиции в исходной. Хранилище обновляет доску только после успешной записи. Отдельное активное изменение `close-action-menus-on-outside-interaction` меняет общий `ActionMenu`, поэтому эту работу нельзя основывать на текущих деталях его закрытия.

## Goals / Non-Goals

**Goals:** использовать существующую операцию сохранения для обоих способов перемещения; восстановить фокус после успешного переноса, когда исходный DOM-узел исчезает; сохранить управление на телефоне без наложения кнопок на название карточки.

**Non-Goals:** изменение схемы IndexedDB, новые доменные операции и библиотека drag-and-drop.

## Decisions

1. **Вычислять соседние статусы из порядка доски в представлении.** `StatusColumn` передаёт `CardView` индекс текущего статуса и соседние статусы. Каждая стрелка — семантическая кнопка с видимой иконкой и доступным именем, включающим направление и целевой статус. Недоступная стрелка остаётся на месте с `disabled`. Это использует текущую модель доски; отдельное хранение соседства создало бы риск рассинхронизации при перестановке статусов.
2. **Вызывать существующий перенос сразу и ждать результата.** Кнопки блокируются на время записи, чтобы повторные быстрые нажатия не создавали гонку. Представление получает признак успешности из текущего метода хранилища; при ошибке доска не меняется, а существующее сообщение о сбое остаётся видимым. Альтернатива — оптимистический перенос с откатом — усложнила бы локальное сохранение без заметной пользы для этого действия.
3. **Оставить дальний переход вторичным действием.** Меню предлагает «Переместить в…» лишь при наличии другого статуса. Список в форме состоит из остальных статусов в порядке доски, а начальный выбор — первый доступный. Это исключает текущую ситуацию, когда подтверждение формы с исходным статусом ничего не делает. Меню и форма остаются совместимыми с отдельной работой по закрытию меню.
4. **Управлять фокусом на уровне доски после успешного переноса.** Перед вызовом сохранения представление фиксирует идентификатор карточки и то, был ли перенос инициирован с клавиатуры. После обновления доски оно находит контроль этой карточки в новом статусе и устанавливает фокус через `focus({ preventScroll: true })`: для стрелки — на соответствующую доступную стрелку либо другой доступный контроль карточки, для формы — на контроль карточки. При ошибке фокус остаётся на исходном контроле. Альтернатива — восстановление внутри старого `CardView` — ненадёжна, поскольку этот экземпляр размонтируется при переносе между колонками.

## Risks / Trade-offs

- [Фокус на карточке может оказаться вне видимой части горизонтальной доски] → по согласованному решению не добавлять принудительную прокрутку; проверить последовательность клавиатурной навигации и видимость кнопок на узком экране.
- [Несколько кнопок на небольшой карточке могут сжать название] → проверить компоновку на ширине 320 px и длинных названиях, сохранить читаемый текст и удобные области нажатия.
- [Одновременная реализация изменения общего меню может затронуть пункт дальнего перехода] → интеграционно проверить открытие, выбор, закрытие и фокус после обоих изменений.
