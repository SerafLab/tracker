# Инструкции для агентов

## Принципы реализации

- Be brief.
- Do not preserve backward compatibility.
- Choose the simplest implementation that fully meets the current requirements.
- Prefer established, well-maintained libraries over custom implementations.
- Fix the cause, not the symptom.
- Suggest best practices, even if they may require refactoring.

## Маршрутизация агентов

Основной чат координирует работу и отвечает за интеграцию.
Он отвечает за требования, решения, общение с пользователем и итоговый результат.

Когда пользователь просит реализовать несколько функций:

- Изучить выбранные предложения вместе до начала реализации.
- Выявить зависимости, противоречия и общие контракты.
- Использовать отдельную ветку и рабочее дерево для каждой функции.
- Выполнять независимые функции параллельно.
- Выполнять зависимые функции в порядке зависимостей.
- Объединить принятые функции в одной интеграционной ветке в порядке зависимостей.
- Проверить объединённый результат перед публикацией интеграционной ветки.

Основной чат может изучать код, запускать проверки, согласовывать планы, управлять ветками и рабочими деревьями, проверять изменения, разрешать конфликты интеграции и вносить интеграционные исправления.
Существенную реализацию и независимое исследование по возможности поручать субагентам.
Небольшие задачи выполнять самостоятельно, если делегирование создаёт лишние затраты.

Каждому субагенту давать одну ограниченную задачу и явно определённую область ответственности.
Субагент сообщает основному чату о вопросах и препятствиях; с пользователем общается основной чат.
Основной чат отвечает за проверку и интеграцию порученной работы.

Перед началом пакета функций или запуском субагента прочитать `docs/agents/rules/agent-routing.md`.

## Проверки перед отправкой ветки

`npm ci` настраивает версионируемый хук `.githooks/pre-push`, который запускает `npm run check`. Не обходить хук. CI для pull request выполняет ту же команду; её успешное выполнение обязательно для слияния.

## Асинхронные тесты

CI медленнее локальной машины, поэтому тест, который полагается на тайминг, проходит локально и падает в CI. При написании и изменении тестов:

- После действия, запускающего асинхронную работу (сохранение, загрузку, открытие или закрытие диалога, перенос фокуса), ждать результата: `findBy*`, `waitFor`, в Playwright — `expect(locator)` с автоожиданием. Синхронные `getBy*`, `toHaveFocus()`, `toHaveValue()` и чтения из репозитория допустимы только после такого ожидания.
- Ждать конкретный наблюдаемый результат последнего шага, а не промежуточный признак. Исчезновение диалога не гарантирует возврат фокуса; появление текста не гарантирует запись в хранилище.
- Не использовать фиксированные задержки (`setTimeout`, `waitForTimeout`) и не увеличивать таймауты вместо ожидания условия.
- Новые и изменённые тестовые файлы перед отправкой прогонять повторно: `npx vitest --run --repeats=10 <файлы>`, для e2e — `npx playwright test <файлы> --repeat-each=5`.
- Если тест упал в CI, но проходит локально, искать и исправлять в нём все несинхронизированные проверки, а не только упавшую строку.

## Выборочный просмотр скриншотов

Не открывать скриншоты автоматически после каждого прогона тестов. Просматривать их выборочно при изменениях интерфейса, диагностике конкретной визуальной ошибки или по запросу пользователя. Успешный прогон без изменений UI не требует просмотра PNG или отдельного визуального отчёта. При ошибке сборки или обычного теста сначала читать текст ошибки и относящийся к нему код.

Выбирать экраны, размеры, языки и состояния по затронутому поведению. При изменениях адаптивной вёрстки проверить относящиеся к ним desktop/mobile-размеры; дополнительные изображения открывать для нерешённых вопросов. Явные визуальные критерии приёмки и запросы пользователя выполнять в заданной области. Не просматривать всю матрицу снимков по умолчанию.

В отчёте о визуальной проверке указать фактически просмотренные экраны, размеры, языки, состояния, результат и существенные ограничения. Успешные тесты и сохранённые PNG сами по себе не подтверждают визуальную проверку. Основной чат может использовать отчёт исполнителя без повторного открытия тех же снимков; повторный просмотр нужен при влияющих на отрисовку изменениях после интеграции, нерешённом замечании или запросе пользователя. Это правило не отменяет автоматические проверки и ответственность основного чата за итог.

## Автоматическая доставка функций и жизненный цикл OpenSpec

Запрос пользователя на реализацию функции разрешает весь обычный путь доставки этой функции: локальные ветки и рабочие деревья, коммиты, отправку ветки, создание pull request, слияние после успешных проверок и публикацию, которую запускает слияние в `main`. Не останавливать работу ради отдельных подтверждений этих шагов. Если пользователь явно ограничил задачу планированием, локальными правками или проверкой, соблюдать это ограничение.

1. До отправки ветки проверить реализацию по спецификации и выполнить `npm run check`. Исправлять ошибки проверки и повторять её без отдельного запроса.
2. Перед созданием готового PR перенести дельта-спецификации завершённого изменения в `openspec/specs/` и архивировать изменение OpenSpec в той же ветке. Включить код и закрытие OpenSpec в один PR. Незавершённую работу можно показать в draft PR, но не сливать.
3. Закоммитить готовый результат, отправить ветку и создать PR в `main`. Если PR уже существует, обновить его, не создавать дубликат. Если в репозитории доступно GitHub auto-merge методом squash, включить его. Иначе дождаться успешных проверок GitHub и выполнить squash merge самостоятельно без нового запроса пользователю.
4. Слияние должно происходить только после обязательных проверок GitHub и выполнения защиты `main`. Не обходить неуспешные проверки, защиту ветки или хук перед отправкой. При сбое исправить причину и обновить PR; если автоматическая доставка недоступна из-за настроек или прав GitHub, сообщить точное препятствие.
5. Различать состояния: локально проверено, PR ожидает проверки, слито в `main`, опубликовано. Не называть функцию доставленной до слияния и успешной публикации.

Вопросы о требованиях и продуктовых решениях передавать пользователю, если ответ нельзя вывести из текущих требований. Обычные действия Git и OpenSpec не требуют отдельного подтверждения.

## Синхронизация локальной `main` после слияния

Когда слияние изменений агента на GitHub подтверждено состоянием PR, без запроса пользователя:

1. Проверить текущую ветку и состояние рабочего дерева.
2. Переключиться на локальную ветку `main`.
3. Если рабочее дерево чистое, выполнить `git pull --ff-only origin main`.
4. Проверить, что локальная `main` синхронизирована с `origin/main`.
5. Если ветка функции известна и рабочее дерево чистое, удалить её локально и из `origin` после проверки, что она полностью слита в `main`.
6. Если есть незакоммиченные изменения или конфликт, не перезаписывать и не прятать изменения через stash, а также не удалять ветку автоматически. Сообщить о ситуации и спросить пользователя, как продолжить.
