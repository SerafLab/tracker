# card-details Specification

## Purpose

Позволяет открыть карточку и сохранить её подробности и историю личных заметок, чтобы продолжать дело с нужными сведениями и договорённостями.

## Requirements

### Requirement: Whole-card detail navigation
Система SHALL открывать подробности карточки в панели обычным нажатием на её свободную площадь на доске и семантическим контролом с клавиатуры. Меню и его действия SHALL работать самостоятельно без открытия подробностей. Начатое перетаскивание, его завершение или отмена и жест прокрутки SHALL не открывать подробности карточки.

#### Scenario: User clicks the card body
- **WHEN** пользователь обычно нажимает на название, метку или свободную площадь карточки без перетаскивания и прокрутки
- **THEN** открывается панель именно этой карточки с блоком «Основное» в режиме просмотра; на широком экране доска остаётся видимой и доступной

#### Scenario: User operates card controls
- **WHEN** пользователь нажимает верхнее меню карточки или пункт меню
- **THEN** нажатие не начинает перетаскивание и не открывает подробности вследствие всплытия; выбранное действие выполняет только свою операцию

#### Scenario: Keyboard user opens details
- **WHEN** пользователь фокусирует семантический контроль открытия карточки и нажимает Enter
- **THEN** открываются её подробности, а фокус перемещается в панель

#### Scenario: User chooses editing from the menu
- **WHEN** пользователь выбирает «Редактировать» в меню карточки, в том числе когда эта карточка уже открыта в панели в режиме просмотра
- **THEN** панель этой карточки показывает блок «Основное» в режиме редактирования с сохранёнными основными полями, а фокус находится в поле названия

#### Scenario: User releases a dragged card
- **WHEN** пользователь завершает либо отменяет начатый жест переноса, в том числе без изменения позиции или вне допустимой цели
- **THEN** связанное с жестом отпускание и последующий синтетический клик не открывают карточку, а следующий самостоятельный обычный клик открывает её

#### Scenario: User scrolls from a card
- **WHEN** пользователь прокручивает доску или страницу свайпом, начатым на свободной площади карточки
- **THEN** подробности карточки не открываются и последующий самостоятельный обычный тап сохраняет возможность открытия

#### Scenario: User switches cards from the board
- **WHEN** пользователь нажимает другую карточку при открытой панели
- **THEN** после разрешения несохранённых изменений панель показывает выбранную карточку, а доска остаётся доступной

### Requirement: Addressable card page and board return
Карточка SHALL иметь один адрес для панели и полной страницы. Открытие с доски SHALL показывать панель с возможностью перейти на полную страницу; прямое открытие адреса и перезагрузка SHALL показывать полную страницу. Панель SHALL возвращать к доске своим закрытием, полная страница — действием «Назад к доске». Система SHALL проверять принадлежность карточки проекту и явно обрабатывать отсутствие карточки или проекта.

#### Scenario: User follows a direct address
- **WHEN** пользователь открывает адрес существующей карточки или перезагружает его
- **THEN** полная страница показывает её подтверждённые поля в режиме просмотра и заметки в контексте соответствующего проекта

#### Scenario: User opens a card from the board
- **WHEN** пользователь открывает карточку с доски
- **THEN** панель показывает подробности, адрес браузера становится адресом карточки, а исходная доска остаётся доступной рядом на широком экране

#### Scenario: User expands the panel
- **WHEN** пользователь выбирает «Открыть на всю страницу» в панели
- **THEN** те же подробности показываются на полной странице по тому же адресу с сохранением подтверждённых данных, текущих черновиков и режима блока «Основное»

#### Scenario: User switches several cards and goes back
- **WHEN** пользователь открывает A, затем B и C из доски и нажимает браузерное «Назад»
- **THEN** панель закрывается и отображается исходная доска без промежуточного возврата через B и A

#### Scenario: User reloads an open panel
- **WHEN** пользователь перезагружает адрес карточки при открытой панели
- **THEN** открывается полная страница этой карточки по тому же адресу

#### Scenario: User returns to the board
- **WHEN** пользователь выбирает «Назад к доске» на странице карточки, в том числе открытой напрямую
- **THEN** после разрешения несохранённых изменений открывается родительская доска с актуальными карточками

#### Scenario: User closes the panel
- **WHEN** пользователь закрывает панель её действием закрытия или браузерным «Назад»
- **THEN** после разрешения несохранённых изменений отображается исходная доска с прежним положением прокрутки и фокусом на доступном контроле карточки

#### Scenario: User sees the board return on a narrow screen
- **WHEN** пользователь открывает страницу карточки на узком экране
- **THEN** «Назад к доске» виден перед блоком «Основное», не перекрывает его заголовок и имеет удобную для касания область и видимый фокус

#### Scenario: Requested card is unavailable
- **WHEN** адрес ссылается на отсутствующую карточку или карточку другого проекта
- **THEN** чужие данные не показываются и доступно понятное сообщение с переходом на указанную существующую доску

#### Scenario: Requested project is unavailable
- **WHEN** проект в адресе отсутствует
- **THEN** приложение переходит к каталогу без показа карточки другого проекта

### Requirement: Card description and explicit field saving
В режиме редактирования блок «Основное» SHALL позволять изменить название, необязательное описание, важность и срочность и сохранять эти поля вместе кнопкой «Сохранить». Описание SHALL поддерживать многострочный текст и очистку до пустого значения. Успешное сохранение SHALL возвращать блок к просмотру с подтверждёнными значениями, оставлять подробности открытыми и не сбрасывать черновик заметки. При ошибке блок SHALL оставаться в режиме редактирования с введёнными значениями.

#### Scenario: User saves all basic fields
- **WHEN** пользователь в режиме редактирования меняет название, описание и признаки и выбирает «Сохранить»
- **THEN** все поля сохраняются вместе, блок возвращается к просмотру с подтверждёнными значениями, фокус переходит на карандаш, а доска отражает новые значения

#### Scenario: User saves fields while a note draft is open
- **WHEN** пользователь выбирает «Сохранить» в блоке «Основное» при несохранённом черновике заметки
- **THEN** основные поля сохраняются, подробности остаются открытыми, а черновик заметки не изменяется

#### Scenario: Saving fields fails
- **WHEN** сохранить название, описание или признаки не удаётся
- **THEN** подтверждённые поля и данные доски не изменяются, блок остаётся в режиме редактирования, а введённые поля и черновик заметки остаются доступными для повторной попытки

#### Scenario: User clears the description
- **WHEN** пользователь очищает описание и успешно сохраняет
- **THEN** блок показывает «Нет описания», и описание остаётся пустым после перезагрузки без изменения заметок

#### Scenario: User changes description without changing flags
- **WHEN** пользователь сохраняет только новое описание
- **THEN** порядок карточки внутри своей группы не меняется

#### Scenario: User edits fields and a note together
- **WHEN** пользователь редактирует блок «Основное» и одновременно пишет черновик заметки
- **THEN** оба редактора остаются открытыми независимо, а сохранение одного не сохраняет и не сбрасывает другой

### Requirement: Dated personal note history
Панель и полная страница SHALL показывать отдельные заметки карточки с датами создания и позволять добавить непустую заметку самостоятельным действием. Заметки SHALL отображаться в выбранном пользователем порядке по дате создания, по умолчанию от новых к старым, в стабильном порядке; даты SHALL соответствовать языку интерфейса и локальному часовому поясу. Создание заметки SHALL не сохранять и не сбрасывать черновики основных полей.

#### Scenario: User adds a note
- **WHEN** пользователь вводит многострочный текст и выбирает «Добавить заметку»
- **THEN** после сохранения заметка с датой появляется в истории на месте, соответствующем выбранному порядку, очищается только её поле ввода, а подробности остаются открытыми

#### Scenario: User submits an empty note
- **WHEN** пользователь отправляет пустой или состоящий из пробелов текст заметки
- **THEN** заметка не создаётся, форма показывает ошибку и остаётся доступной

#### Scenario: Card has no notes
- **WHEN** пользователь открывает карточку без заметок
- **THEN** история показывает понятное пустое состояние и доступно добавление первой заметки

#### Scenario: User opens history without a saved order
- **WHEN** пользователь, ещё не выбиравший порядок, открывает карточку с несколькими заметками
- **THEN** самая новая по дате создания заметка показана первой, а самая старая — последней

### Requirement: Editable and confirmed deletable notes
Система SHALL позволять исправить заметку отдельным сохранением и удалить её только после подтверждения, идентифицирующего запись. У сохранённой заметки действия редактирования и удаления SHALL отображаться как иконки карандаша и корзины в стиле остальных иконок приложения, с локализованными доступными именами, удобной для касания областью и видимым фокусом. Обе иконки SHALL иметь видимый размер 16 × 16 px при области нажатия не менее 44 × 44 px и находиться справа от даты создания над текстом заметки в панели и на полной странице. На узком экране дата и отметка изменения SHALL оставаться читаемыми, при необходимости переносясь в своей части строки без перекрытия действий и горизонтальной прокрутки. Кнопки добавления и сохранения заметки и отмены редактирования SHALL сохранять текстовые подписи. Изменение SHALL сохранять исходную дату и позицию и показывать отметку «изменено»; сохранение прежнего текста SHALL не создавать отметку. Отмена SHALL сохранять запись.

#### Scenario: User edits an existing note
- **WHEN** пользователь сохраняет изменённый непустой текст заметки
- **THEN** текст обновляется с отметкой изменения, исходной датой и прежним местом в истории

#### Scenario: User saves an unchanged note
- **WHEN** пользователь сохраняет текст без фактических изменений
- **THEN** дата изменения и отметка изменения не добавляются и не обновляются

#### Scenario: User confirms note deletion
- **WHEN** пользователь подтверждает удаление выбранной заметки
- **THEN** удаляется только эта заметка, результат сохраняется после перезагрузки, фокус остаётся на доступном контроле истории

#### Scenario: User cancels note deletion
- **WHEN** пользователь отменяет подтверждение удаления
- **THEN** заметка остаётся без изменений

#### Scenario: User views actions beside creation date
- **WHEN** пользователь открывает сохранённую заметку в панели или на полной странице
- **THEN** карандаш и корзина размером 16 × 16 px расположены справа от даты создания над текстом, а каждая кнопка имеет область нажатия не менее 44 × 44 px

#### Scenario: User views an edited note on a narrow screen
- **WHEN** пользователь открывает изменённую заметку с длинной локализованной датой на экране шириной 320 px
- **THEN** дата и отметка изменения читаемы, могут переноситься в левой части строки, а обе кнопки остаются справа без перекрытия и горизонтальной прокрутки

### Requirement: Plain text with usable web links
Описание и заметки SHALL сохранять многострочный обычный текст и показывать абсолютные HTTP/HTTPS ссылки как кликабельные. HTML и Markdown SHALL отображаться как текст. Открытие веб-ссылки SHALL сохранять открытые подробности и их черновики.

#### Scenario: User views multiline text and a URL
- **WHEN** сохранённый текст содержит переносы строк и абсолютную HTTPS ссылку
- **THEN** переносы сохраняются, ссылка доступна мышью и клавиатурой и открывается отдельно от карточки

#### Scenario: User saves markup or another URL scheme
- **WHEN** пользователь сохраняет HTML, Markdown или адрес javascript/data
- **THEN** содержимое не исполняется как разметка или код и опасный адрес не становится активной ссылкой

### Requirement: Guarded navigation with unsaved drafts
При несохранённых основных полях или черновике новой/редактируемой заметки система SHALL перед закрытием панели, переключением карточки, внутренним переходом, Back/Forward или управляемым обновлением приложения предлагать сохранить и выйти, выйти без сохранения или остаться. Переход после сохранения SHALL происходить только при успехе всех ожидающих сохранений.

#### Scenario: User leaves after saving drafts
- **WHEN** пользователь выбирает «Сохранить и выйти», а основные поля и заметка корректны и записаны
- **THEN** применяется исходно выбранный переход без повторного подтверждения и без дублирования заметки

#### Scenario: User discards pending changes
- **WHEN** пользователь выбирает «Выйти без сохранения»
- **THEN** только оставшиеся черновики отбрасываются и выбранный переход выполняется

#### Scenario: User remains on the page
- **WHEN** пользователь выбирает «Остаться», закрывает диалог или нажимает Escape
- **THEN** текущая панель или страница, значения черновиков и текущая запись навигации сохраняются

#### Scenario: User switches cards with a draft
- **WHEN** пользователь нажимает другую карточку на доске при несохранённых полях или заметке в панели
- **THEN** до переключения система предлагает три действия; выбор «Остаться» сохраняет прежнюю карточку и черновики, а ошибка сохранения не показывает другую карточку

#### Scenario: Saving only partly succeeds
- **WHEN** при «Сохранить и выйти» основные поля записаны, но сохранить заметку не удалось
- **THEN** переход не выполняется, поля остаются подтверждёнными, текст заметки остаётся черновиком с ошибкой и доступной повторной попыткой без дубликатов

#### Scenario: User switches note editors
- **WHEN** пользователь начинает другую заметку при несохранённом тексте текущей
- **THEN** текущий черновик защищён тем же выбором перед переключением

#### Scenario: User reloads or closes the browser
- **WHEN** пользователь пытается нативно перезагрузить открытые подробности или закрыть вкладку с черновиком
- **THEN** приложение запрашивает стандартное браузерное предупреждение, если браузер его поддерживает, без обещания сохранения при закрытии

#### Scenario: User activates an app update
- **WHEN** пользователь выбирает обновление приложения при наличии черновиков
- **THEN** управляемая активация и перезагрузка ждут решения guard; отмена или ошибка сохранения оставляет текущую панель или страницу

### Requirement: Local durable note operations and failures
Описание, заметки и их даты SHALL сохраняться локально, работать офлайн и не меняться при переносе карточки. При ошибке операции заметки подтверждённые данные SHALL оставаться прежними, введённое SHALL сохраняться для повторной попытки и успех SHALL не объявляться.

#### Scenario: User returns offline
- **WHEN** пользователь сохраняет описание и заметки, повторно открывает установленное приложение без сети
- **THEN** сохранённые данные доступны и новые локальные изменения можно сохранить

#### Scenario: User moves a detailed card
- **WHEN** пользователь переносит карточку в другой статус
- **THEN** описание, заметки и даты сохраняются у той же карточки

#### Scenario: A note operation fails
- **WHEN** создание, изменение или удаление заметки не удаётся записать
- **THEN** история остаётся в последнем подтверждённом состоянии, редактор/подтверждение остаётся доступным с введённым текстом и сообщением об ошибке

### Requirement: Accessible localized detail page
Панель, полная страница и диалоги SHALL быть доступны с клавиатуры и на ширине 320 px, иметь подписанные поля, видимый фокус и русские/английские подписи и ошибки. На узком экране подробности, открытые с доски, SHALL занимать экран целиком. Длинные тексты и ссылки SHALL не перекрывать действия и не создавать горизонтального переполнения. Пользовательский текст SHALL не переводиться.

#### Scenario: User works on a narrow screen in English
- **WHEN** пользователь открывает карточку с длинными текстами при английском интерфейсе на ширине 320 px
- **THEN** поля, история, ссылки, даты и действия доступны и читаемы без горизонтального scroll страницы, подписи и ошибки английские

#### Scenario: User interacts with confirmation using a keyboard
- **WHEN** пользователь открывает подтверждение удаления или ухода с черновиком
- **THEN** фокус входит в диалог и остаётся внутри него, а отмена возвращает его к вызвавшему действию

#### Scenario: User opens details on a narrow screen
- **WHEN** пользователь открывает карточку с доски на узком экране
- **THEN** подробности занимают весь экран, действия закрытия и сохранения доступны, а доска остаётся доступной после закрытия

#### Scenario: Keyboard user works with the panel and board
- **WHEN** пользователь открывает панель с клавиатуры, сохраняет поля и возвращается к доске
- **THEN** фокус последовательно попадает в панель и возвращается к доступному контролу карточки; доска и панель имеют различимые названия областей

### Requirement: Read-only card summary with explicit editing
Панель и полная страница SHALL показывать блок «Основное» с названием карточки как заголовком, метками важности и срочности того же вида, смысла, порядка и положения относительно названия и описания, что на доске, и описанием со ссылками. По умолчанию блок SHALL быть только для чтения и предлагать один контрол редактирования в виде карандаша с локализованным доступным именем, видимым фокусом и областью нажатия не менее 44 × 44 px. Описание SHALL не показываться повторно в другом блоке.

#### Scenario: User opens a card
- **WHEN** пользователь открывает карточку с названием, обоими признаками и описанием со ссылкой
- **THEN** блок «Основное» показывает название как заголовок, затем метки «Важная» и «Срочная» в том же порядке, что на доске, затем описание с активной ссылкой, без полей ввода и без второго блока описания

#### Scenario: Card has no flags and no description
- **WHEN** пользователь открывает карточку без признаков и с пустым описанием
- **THEN** меток нет, а вместо описания показан приглушённый текст «Нет описания»

#### Scenario: User enters editing
- **WHEN** пользователь нажимает карандаш блока «Основное»
- **THEN** блок показывает поля названия, описания и переключатели важности и срочности с подтверждёнными значениями, кнопки «Отмена» и «Сохранить», а фокус переходит в поле названия

#### Scenario: User recognizes flags while editing
- **WHEN** блок «Основное» находится в режиме редактирования
- **THEN** подписи переключателей важности и срочности содержат символ и цвет соответствующей метки доски и остаются понятными без различения цветов

#### Scenario: User cancels unchanged editing
- **WHEN** пользователь нажимает «Отмена» без изменений основных полей
- **THEN** блок возвращается к просмотру, а фокус переходит на карандаш

#### Scenario: User cancels changed editing
- **WHEN** пользователь нажимает «Отмена» при несохранённых изменениях основных полей
- **THEN** предлагается тот же выбор, что при уходе с черновиками; «Остаться» сохраняет режим редактирования и введённые значения

#### Scenario: Agent changes a card being viewed
- **WHEN** подтверждённые поля карточки изменяются вне блока, пока он находится в режиме просмотра
- **THEN** блок показывает новые подтверждённые значения

### Requirement: Card detail headers without repeated context
Шапка панели SHALL содержать только «Открыть на всю страницу» и закрытие. Полная страница SHALL предоставлять «Назад к доске» без названия проекта. Ни панель, ни страница SHALL не показывать название проекта или статус карточки в своём содержимом.

#### Scenario: User views panel header
- **WHEN** пользователь открывает карточку с доски
- **THEN** шапка панели содержит «Открыть на всю страницу» и крестик, а в панели нет названия проекта, статуса и кнопки «Назад к доске»

#### Scenario: User views the full page
- **WHEN** пользователь открывает полную страницу карточки
- **THEN** перед блоком «Основное» находится «Назад к доске» без названия проекта, а отдельной строки статуса нет

### Requirement: Selectable note history order
У заголовка истории заметок в панели и на полной странице SHALL быть иконка-переключатель порядка «сначала новые» / «сначала старые». Иконка SHALL визуально различать текущий порядок, иметь локализованное доступное имя с текущим порядком, видимый фокус, видимый размер 16 × 16 px и область нажатия не менее 44 × 44 px. Переключение SHALL сразу переупорядочивать историю и не затрагивать черновики, заметки и их даты.

#### Scenario: User switches the order
- **WHEN** пользователь при порядке «сначала новые» активирует переключатель мышью или клавиатурой
- **THEN** история показывается от старых к новым, доступное имя и иконка сообщают порядок «сначала старые», а фокус остаётся на переключателе

#### Scenario: User switches the order with drafts open
- **WHEN** пользователь переключает порядок при открытых черновиках основных полей или заметки
- **THEN** черновики и их тексты сохраняются, а редактируемая заметка остаётся в своём редакторе

#### Scenario: Edited note keeps its place
- **WHEN** пользователь изменяет старую заметку при любом порядке
- **THEN** заметка остаётся на месте, определяемом её датой создания

#### Scenario: User views the toggle on a narrow screen
- **WHEN** пользователь открывает историю на ширине 320 px в английском интерфейсе
- **THEN** заголовок и переключатель читаемы и доступны без перекрытия и горизонтальной прокрутки, а доступное имя переключателя английское

### Requirement: Persistent application-wide note order
Выбранный порядок заметок SHALL сохраняться в браузере и применяться ко всем карточкам и проектам после повторного открытия и перезагрузки. Если сохранить выбор не удаётся, выбранный порядок SHALL действовать до перезагрузки без ошибки для пользователя. Неизвестное или отсутствующее сохранённое значение SHALL означать «сначала новые».

#### Scenario: User reloads after choosing an order
- **WHEN** пользователь выбирает «сначала старые» в одной карточке и перезагружает приложение
- **THEN** история этой и любой другой карточки показывается от старых к новым

#### Scenario: Browser storage is unavailable
- **WHEN** сохранение выбора в браузере завершается ошибкой
- **THEN** порядок меняется до перезагрузки, заметки и черновики не затрагиваются, а после перезагрузки действует «сначала новые»

### Requirement: Note creation on the newest side
Кнопка «Добавить заметку» и редактор новой заметки SHALL располагаться со стороны новых заметок: над списком при порядке «сначала новые» и под списком при порядке «сначала старые». В пустой истории они SHALL располагаться после пустого состояния.

#### Scenario: User adds a note with newest first
- **WHEN** при порядке «сначала новые» пользователь открывает добавление заметки и сохраняет её
- **THEN** редактор находится над списком, а сохранённая заметка появляется первой в истории

#### Scenario: User adds a note with oldest first
- **WHEN** при порядке «сначала старые» пользователь открывает добавление заметки
- **THEN** редактор находится под списком, а сохранённая заметка появляется последней в истории

### Requirement: Deletion focus follows the shown order
После подтверждённого удаления заметки фокус SHALL переходить на действие соседней заметки в показанном порядке: следующей, а при её отсутствии — предыдущей; при пустой истории — на добавление заметки.

#### Scenario: User deletes a note with newest first
- **WHEN** при порядке «сначала новые» пользователь удаляет вторую из трёх показанных заметок
- **THEN** фокус переходит на действие заметки, которая была показана третьей
