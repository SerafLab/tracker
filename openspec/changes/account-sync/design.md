# Design

## Context

- Данные проектов лежат в Dexie 4, схема v3, база `personal-project-tracker`, таблицы `projects`, `statuses`, `cards`, `notes` и локальная `workspace` (`lastProjectId`). Ключи — строки `crypto.randomUUID()`. Dexie доступен только инфраструктуре фичи `project-board` (`scripts/check-architecture.mjs`).
- Репозиторий пишет существующие записи через `put`/`bulkPut` и перенумеровывает позиции подряд с нуля. Каскадное удаление проекта сначала читает ключи детей, затем удаляет их по ключам. `snapshot()` отдаёт записи как есть.
- Целостность копии (`checkBackupIntegrity`) требует уникальных ID, существующих владельцев, позиций подряд с нуля и порядка групп. Строгая Zod-схема отклоняет лишние поля.
- Страница настроек и сборка разделов появляются в `settings-page` (решение 4 его design.md). Это изменение добавляет раздел в начало массива и заменяет вид шестерёнки.
- Публикация — GitHub Pages `https://seraflab.github.io/tracker/`, Service Worker генерируется (ADR-0003). Своего сервера нет.

Документация Dexie Cloud, на которую опирается дизайн:
- настройка клиента: https://dexie.org/cloud/docs/db.cloud.configure()
- аутентификация, свой интерфейс входа, провайдеры OAuth: https://dexie.org/cloud/docs/authentication
- слияние по полям и операции с условием: https://dexie.org/cloud/docs/consistency
- ключи и запрет миграций синхронизируемых таблиц: https://dexie.org/cloud/docs/best-practices
- состояние синхронизации: https://dexie.org/cloud/docs/SyncState
- пользователь и лицензия: https://dexie.org/cloud/docs/UserLogin
- удаление пользователя через REST: https://dexie.org/cloud/docs/rest-api
- разрешённые origin и импорт: https://dexie.org/cloud/docs/cli
- тарифы, оценочные пользователи и ограничение входа: https://dexie.org/cloud/pricing

## Goals / Non-Goals

**Goals:**
- Логику аккаунта и синхронизации можно проверять без настоящего Dexie Cloud через порт и фальшивый адаптер.
- Без входа приложение ведёт себя как сейчас; облако не нужно для запуска, офлайна и тестов.
- Слияние двух устройств не нарушает порядок и целостность, которые проверяет резервная копия.

**Non-Goals:**
- Фоновая синхронизация в Service Worker и периодическая синхронизация.
- Совместные проекты, роли и приглашения в realm Dexie Cloud.
- Capacitor, Sign in with Apple, оплата, свой домен, политика конфиденциальности. Решения ниже их не блокируют.
- Синхронизация настроек устройства.

## Decisions

1. **Аддон на существующей базе.** `ProjectBoardDatabase` получает `addons: [dexieCloud]` и `db.cloud.configure({ databaseUrl, requireAuth: false, customLoginGui: true, unsyncedTables: ['workspace'], nameSuffix: false, tryUseServiceWorker: false })`.
   - `nameSuffix: false` сохраняет имя базы, поэтому данные, созданные до входа, остаются на месте и выгружаются при первом входе. При `true` аддон открыл бы другую базу IndexedDB, и прежние проекты пропали бы из интерфейса. Проверяется в П1.
   - Схема v4 повторяет хранилища v3 без `upgrade()`. С этой версии синхронизируемые таблицы не мигрируют на клиенте (best-practices); новые поля только добавляются и читаются с умолчанием. Это записывается в ADR-0006.
   - `tryUseServiceWorker: false`: синхронизация идёт на странице, сгенерированный Service Worker (ADR-0003) не меняется.
   - Альтернатива — отдельная облачная база и копирование данных при входе. Отклонена: двойной источник правды и своя логика переноса.

2. **Адрес базы задаётся сборкой.** `VITE_DEXIE_CLOUD_URL` в production-сборке. Без него аддон не подключается, раздел «Аккаунт и синхронизация» не показывается, значок остаётся контуром человека без меню входа. Тестовые сборки задают `VITE_CLOUD=fake`, и приложение использует фальшивый адаптер; production-сборка его не содержит (условие на `import.meta.env` вырезается сборщиком). Так e2e не обращаются к облаку.

3. **Порт и адаптер.** Новая фича `src/features/account/` со слоями как у `project-board`; `check-architecture.mjs` обобщается на `features/*`.
   - `domain/account-view.ts` — чистая функция `accountView(user, sync, online)` → `signedOut | syncing | synced | offline | error | reloginNeeded | notInvited`, плюс буква значка и признак «нужно действие». Таблица соответствия — решение 9.
   - `application/cloud-account.ts` — порт `CloudAccount`: `subscribe(listener)` со снимком `{ user, sync, interaction }`, `requestCode(email)`, `submitCode(code)`, `signInWithGoogle()`, `unsyncedChanges()`, `retry()`, `signOut()`, `deleteAccount()`. Use cases: `beginSignIn` (счёт проектов и решение о диалоге объединения), `signOut` (проверка несинхронизированного), `deleteAccount`.
   - `infrastructure/dexie-cloud-account.ts` — адаптер над `db.cloud.currentUser`, `db.cloud.syncState`, `db.cloud.userInteraction`, `db.cloud.login`, `db.cloud.logout`, `db.cloud.sync` и REST. Экземпляр `db.cloud` передаёт оболочка из `project-board` через публичный `index.ts`.
   - `infrastructure/fake-cloud-account.ts` — управляемый из теста адаптер: e-mail, код, сеть, ошибки, срок сеанса.
   - Альтернатива — вызывать `db.cloud` прямо из компонентов. Отклонена: без облака такие компоненты не проверить.

4. **Свой интерфейс входа.** `customLoginGui: true`; адаптер переводит `userInteraction` (`email`, `otp`, `message-alert`, `logout-confirmation`) в события порта. Код: `db.cloud.login({ email, grant_type: 'otp' })`, затем `onSubmit({ otp })`. Google: `db.cloud.login({ provider: 'google', redirectPath })` с возвратом на `#settings`; используется redirect-поток, другого документация не описывает. Будущий Apple — ещё одно значение `provider`; Capacitor — `redirectPath` со своей схемой и `handleOAuthCallback`.

5. **Объединение до входа.** Диалог «На устройстве N проектов…» показывается до вызова `login`, потому что Dexie Cloud выгружает локальные данные сразу после входа, а Google-вход уводит со страницы. «Отмена» не вызывает `login`. Объединение по ID — штатное поведение: ключи UUID уникальны глобально (best-practices допускают собственные строковые ключи с энтропией GUID). Проверяется в П1–П2.

6. **Запись изменений полями.** Все изменения существующих записей переходят с `put`/`bulkPut` на `update`/`bulkUpdate` только изменённых полей: `put` заменяет объект целиком и отменяет слияние по полям (consistency). Создание остаётся `add`.

7. **Каскад и «сироты».** Каскадное удаление проекта и статуса выполняется операциями с условием: `cards.where('statusId').anyOf(statusIds).delete()` и аналогично для заметок. Сервер повторяет такие операции для изменений устройств, которые были офлайн (consistency), поэтому карточка, добавленная офлайн в удалённый статус, тоже удаляется. Оставшиеся «сироты» (например, заметка карточки, созданной офлайн в удалённом статусе) отфильтровываются при чтении и выгрузке.

8. **Сходящийся порядок.** Чтение сортирует статусы по `(position, id)`, карточки — по `(группа по убыванию, position, id)`, так что повторы и пропуски позиций после слияния дают одинаковый порядок на всех устройствах. Каждая запись порядка перенумеровывает затронутый список подряд с нуля. `snapshot()` для копии берёт только поля доменных типов (без `realmId`, `owner` и других служебных), отбрасывает «сирот» и нормализует позиции, поэтому копия проходит существующую проверку целостности без её ослабления.
   - Альтернатива — дробные ключи порядка. Отклонена сейчас: это изменение схемы, а синхронизируемые таблицы мигрировать нельзя. Вернуться к ней, если перестановки на двух устройствах начнут заметно «прыгать».

9. **Состояние синхронизации** (SyncState: `status`, `phase`, `license`):

   | Условие | Текст | Точка на значке |
   | --- | --- | --- |
   | нет пользователя | без входа | нет |
   | `license` `expired`/`deactivated` или отказ в обновлении токена | «Нужно войти снова» | да |
   | `phase = error` или `status = error` | «Ошибка синхронизации» + «Повторить» | да |
   | `status` `offline`/`disconnected` или `navigator.onLine = false` | «Нет сети, изменения сохранены на устройстве» | нет |
   | `phase` `pushing`/`pulling`/`initial`/`not-in-sync` | «Синхронизация…» | нет |
   | `phase = in-sync` | «Синхронизировано» | нет |

   Точное поведение при истёкшем токене и при ошибке без сети уточняет П6.

10. **Выход.** Use case проверяет несинхронизированные изменения через адаптер. Если они есть, показывается предупреждение с «Выгрузить копию», «Отмена», «Выйти всё равно». Затем `db.cloud.logout()`; адаптер гарантирует, что после выхода таблиц данных проектов на устройстве нет, а `workspace` очищена. Если документированный `logout` этого не делает, адаптер очищает таблицы сам (П6).

11. **Удаление аккаунта.** `DELETE {databaseUrl}/users/{userId}` с токеном доступа текущего пользователя: «Any user have the permission to delete themselves» (rest-api). После успеха — выход с удалением данных на устройстве. Без сети кнопка подтверждения недоступна. Проверяется в П8.

12. **Ограничение входа.** Цель — ограничение на стороне Dexie Cloud: тарифная страница говорит, что вход всем открыт по умолчанию и это настраивается. Отказ сервера адаптер переводит в `notInvited`. Если серверного ограничения нет, это «стоп» для ДОПУЩЕНИЯ: решение принимает пользователь (открытый вход с оценочной лицензией 30 активных дней или свой сервер выдачи токенов через `fetchTokens`). Автор переводит свою учётную запись в production-место в Dexie Cloud Manager.

13. **Стратегия идентичности — e-mail** (по умолчанию), чтобы вход кодом и через Google с тем же адресом давал одного пользователя. Её нельзя менять после появления пользователей (authentication). Проверяется в П4.

14. **Значок аккаунта.** `AppBar` читает из контекста `src/ui` вид значка `{ kind: 'person' | 'initial', initial?, attention?: 'relogin' | 'error' }`, который задаёт оболочка из состояния фичи `account`. В служебных состояниях — контур человека без точки.

15. **WebMCP** не меняется: инструменты пишут через тот же репозиторий, а синхронизация разносит изменения. Требование «Browser storage remains authoritative» остаётся верным: интеграция агента сама ничего не синхронизирует.

## Risks / Trade-offs

- [Закрытый сервер, привязка к поставщику] → выход — существующая выгрузка JSON; формат копии не зависит от Dexie Cloud.
- [Схема v4 не открывается прежней версией] → откат выпуска невозможен без исправления вперёд (ADR-0002). Перед выпуском — выгрузка копии автором; старые вкладки уже получают «нужен перезапуск».
- [Запрет миграций синхронизируемых таблиц] → поля только добавляются; любое иное изменение данных требует отдельного решения и ADR.
- [Перестановки на двух устройствах офлайн дают неожиданный, но одинаковый порядок] → сходящаяся сортировка (решение 8); дробные ключи — запасной путь.
- [Размер бандла растёт на аддон] → измерить в П9; ленивую загрузку не делаем: аддон подключается при создании базы.
- [Сбой Dexie Cloud] → приложение работает локально, состояние показывает ошибку, данные не теряются.
- [Данные тестировщиков у стороннего обработчика без политики конфиденциальности] → вне рамок по решению пользователя; вынесено в открытые вопросы.

## Migration Plan

1. Прототип П1–П9 на отдельной ветке и тестовой базе Dexie Cloud; результат с решением «продолжать / остановиться» записать в `docs/agents/plans/` до основной реализации.
2. Создать production-базу, добавить origin `https://seraflab.github.io` и локальные адреса разработки (`npx dexie-cloud whitelist`), подключить Google в Dexie Cloud Manager, настроить ограничение входа, перевести учётную запись автора в production.
3. Выпуск: схема v4 с аддоном, вход доступен. Без входа поведение прежнее.
4. Позже Capacitor добавит свои origin и `redirectPath`; Apple — провайдера в Manager.
