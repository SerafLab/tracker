# Design

## Context

Мотивация — в proposal.md. Сейчас ProjectCatalogueView использует общий NameDialog, а createProject передаёт только имя через ProjectBoardApp, Zustand и application/use-cases.ts. DexieProjectBoardRepository создаёт проект и lastProjectId одной транзакцией, не затрагивая statuses. Статусы хранят обычное имя и position, без типа завершения. i18next уже поддерживает ru/en. Тесты создания во многих местах предполагают пустую доску; e2e/app-bar.spec.ts также ожидает отсутствие любых combobox в диалоге.

## Goals / Non-Goals

**Goals:**
- Сохранить архитектурные границы: переводы разрешаются на стороне представления, application и repository получают обычные названия.
- Сохранить и открыть полную доску одним созданием, без видимого промежуточного состояния.
- Использовать существующие модальные механизмы и локальное хранилище.

**Non-Goals:**
- Сущность постоянного шаблона, связь проекта с версией набора, миграция существующих проектов.
- Изменение формы переименования, специальная семантика конечных статусов, новые зависимости.

## Decisions

### 1. Каталог наборов и граница переводов

В представлении определить один типизированный каталог с устойчивыми ID simple/search/documents/development/job-search и упорядоченными ключами переводов. В resources.ts добавить симметричные русские и английские значения по дельта-спецификациям. Пустой вариант соответствует пустому списку. Формировать предварительный список и отправляемые названия из одной функции, разрешая текущий язык при отправке.

Альтернатива — хранить presetId и переводить названия при отображении — нарушает согласованное поведение сохранённых имён. Постоянно хранить ID набора не требуется: он нужен только форме.

### 2. Единый явный контракт создания

Вместо строкового аргумента использовать CreateProjectInput с name и initialStatusNames: string[]. Передавать его через ProjectCatalogueView → ProjectBoardApp → state → application. Application проверяет непустое имя проекта и каждого переданного статуса, создаёт идентификаторы и передаёт проект с упорядоченными записями статусов в repository. Пустой массив явно означает «Без статусов». Общие типы разместить внутри модуля project-board согласно архитектурным ограничениям; не импортировать i18next в domain/application.

Это проще зависимости application от языка и не требует сохранять старую строковую сигнатуру. Обновить все текущие вызовы и заглушки; не вводить совместимую перегрузку. Возможная будущая MCP-интеграция должна использовать тот же контракт с явными начальными названиями, но её реализация не входит в это изменение.

### 3. Одна транзакция сохранения

Расширить repository.createProject: транзакция rw охватывает projects, statuses и workspace; в ней записать проект, статусы с position от 0 и lastProjectId. Не вызывать createStatus последовательными внешними мутациями: частичная ошибка оставит неполную доску. Существующая схема IndexedDB уже подходит, повышение версии не нужно.

### 4. Отдельная форма создания проекта

Создать ProjectCreateDialog на основе ActionDialog, сохранив NameDialog для переименования. Под именем разместить подписанный нативный select и упорядоченный предварительный список выбранных статусов; для пустого варианта — короткое пояснение. Нативный select уменьшает объём кода и уже поддерживается управлением фокусом ActionDialog. При каждом открытии устанавливать simple; не запоминать прошлый выбор.

Передавать из onCreate явный результат успеха. При ошибке оставлять форму, имя и выбор на месте, показывать локализованную ошибку. Блокировать повторную отправку на время запроса, включая синхронный pending guard. Переходить на доску и сообщать onMutationSaved только после успешной записи. Различать ошибку записи и сбой последующей навигации: сохранённый проект не создавать повторно из-за ошибки перехода. Сохранить существующий перенос фокуса после создания и возврат к кнопке при отмене.

## Risks / Trade-offs

- [Тесты завязаны на пустой проект] → В сценариях ручной сборки явно выбирать «Без статусов»; отдельными тестами проверить новое поведение по умолчанию. Не ослаблять проверки состава доски.
- [Select набора ошибочно принимается тестами за выбор языка] → Проверять элементы по доступным именам и области settings; язык по-прежнему недоступен в диалоге.
- [Пять статусов требуют прокрутки] → Проверить доступность всех статусов на мобильном и отсутствие переполнения страницы; не вводить новое требование уместить пять колонок на desktop.
- [Переводы превратятся в динамические названия] → Сохранять только строки и проверить смену языка после пользовательского переименования.
- [Параллельные изменения каталога/репозитория] → При реализации учесть add-project-deletion, add-card-details и add-agent-mcp-integration, если они уже интегрированы; это не предварительные зависимости этого изменения.

## Migration Plan

Изменение не мигрирует данные. Обновить все внутренние вызовы создания и тесты одновременно, выполнить npm run check. Перед готовым PR синхронизировать дельты и архивировать изменение по правилам репозитория. Откат кода не требует удаления или преобразования созданных статусов: они имеют существующую структуру записей.
