# Design

## Context

Текущий сценарий доски был намеренно реализован в небольшом наборе файлов: `src/main.tsx` содержит app startup, hash-навигацию, асинхронную загрузку, мутации и React-представление, а `src/domain.ts` и `src/storage.ts` содержат модель и Dexie-репозиторий. Уже принятые ADR-0001 и ADR-0002 закрепляют статическое local-first приложение и нормализованное IndexedDB-хранилище с forward-only миграциями.

Этот change реорганизует уже работающий сценарий, описанный активным change `add-persistent-project-board`, не меняя его спецификацию и schema v1. Мотивация и границы — в [proposal.md](proposal.md).

## Goals / Non-Goals

**Goals:**

- Установить одну понятную границу feature-модуля для текущего сценария доски и направленные зависимости внутри него.
- Сделать Zustand единственным источником подтверждённого runtime-состояния, из которого читает React.
- Изолировать domain и application от React, браузерных API и Dexie, сохранив текущие сценарии и данные браузера.
- Оставить `app` единственным местом, которое создаёт зависимости и взаимодействует с hash-навигацией.
- Превратить правила архитектуры в автоматические проверки, а не неформальную договорённость.

**Non-Goals:**

- Не выделять отдельные feature-модули для проекта, статуса и карточки: они составляют один пользовательский сценарий и одну согласованную модель доски.
- Не вводить сервер, аккаунты, синхронизацию, очереди, разрешение конфликтов или конкретный мобильный runtime.
- Не менять database name, таблицы, ключи, записи, Dexie version 1 или формат существующих данных.
- Не переносить краткоживущие состояния формы — значения input, фокус и режим редактирования — в Zustand.

## Decisions

### Модульный монолит с одним feature `project-board`

Структура исходников будет разделена на `app/` и `features/project-board/`. `app/` создаёт адаптеры и store, подключает React и отображает/изменяет hash. Feature владеет текущим пользовательским сценарием и содержит следующие внутренние области:

```text
src/
  app/                         # composition root и hash-routing
  features/project-board/
    domain/                    # типы, инварианты и чистые правила
    application/               # use cases и порт репозитория
    infrastructure/indexeddb/  # Dexie database и реализация порта
    state/                     # создаваемый Zustand store и actions
    presentation/              # React views; CardView получает props/callbacks
    index.ts                   # единственная публичная точка feature
```

Внутренние файлы feature не импортируются извне кроме разрешённых точек композиции. Разделение по техническим корневым папкам всего приложения (`components`, `services`, `repositories`) отвергнуто: с ростом возможностей связанные изменения будут распределяться между многими папками. Полная hexagonal/clean architecture с портом для каждого UI-взаимодействия отвергнута как преждевременная сложность для одного feature.

### Направление зависимостей и порт данных

`domain` не зависит ни от чего внешнего. `application` определяет use cases и минимальный асинхронный порт `ProjectBoardRepository`; он работает с доменными типами и возвращает подтверждённые снимки каталога или доски. `infrastructure/indexeddb` реализует этот порт через Dexie и является единственным кодом, который импортирует Dexie или знает таблицы IndexedDB.

Zustand actions вызывают application use cases; после успешного ответа записывают возвращённое подтверждённое состояние в store. При ошибке они сохраняют последний подтверждённый снимок и выставляют наблюдаемую ошибку. Прямой доступ store или React к Dexie отвергнут: он смешивает runtime-состояние, правила и детали хранения, что усложнит замену или добавление удалённого адаптера.

Порт сразу остаётся `async` и сообщает об ошибках. Это готовит замену либо композицию адаптеров для будущей синхронизации, но не определяет её модель, конфликтную политику или серверный API.

### Zustand для подтверждённого состояния, React state для временного UI

Один store feature владеет состоянием startup/loading, каталогом либо выбранной доской, ошибкой сохранения и actions сценария. React-представление читает эти данные через selectors; оно не хранит вторую копию доски. `NameForm`, `RenameControl`, `CardView` и подобные компоненты принимают данные и callbacks через props и держат только краткоживущие UI-детали локально.

Контекст React или набор независимых `useState` в корневом компоненте отвергнуты: они снова сделают entry-файл владельцем модели сценария. Хранение каждого символа ввода в Zustand отвергнуто как ненужная глобализация эфемерного состояния.

### App владеет браузером и композиционными решениями

Hash parsing, подписка на `hashchange`, запись маршрута и создание конкретных реализаций остаются в `app`. Этот слой передаёт feature выбранный project id или навигационный callback, не позволяя domain, application или state импортировать `location`, `addEventListener` или Dexie. Это сохраняет сценарий пригодным для другого UI/runtime без обещания общего мобильного пакета.

### Архитектурный контракт как часть проверок

В проект добавляется статическая проверка графа импортов с явными разрешёнными направлениями и публичными entry points; она выполняется локально и в GitHub Actions перед production build. Тесты разделяются по ответственности: чистые domain-правила, application use cases с тестовой реализацией порта, контракт/интеграция Dexie-адаптера, Zustand state transitions и существующий наблюдаемый React-сценарий. Это предпочтительнее соглашения в README, потому что прямой импорт инфраструктуры проявится только при следующем изменении.

## Risks / Trade-offs

- [Zustand создаёт дополнительный слой в маленьком приложении] → ограничить store одним feature и подтверждённым runtime-состоянием; не вводить универсальные stores или middleware.
- [Рефакторинг изменит порядок/атомарность текущих операций] → сохранить Dexie-схему и транзакционные границы, добавить регрессионные тесты на данные schema v1, порядок и неуспешные записи.
- [Проверка импортов будет обходиться через относительные пути] → запретить такие пути к внутренностям feature в настройке статической проверки и сделать проверку обязательной в workflow.
- [Будущий сервер потребует иной read/write модели] → закрепить только async-порт и domain/application independence; спроектировать синхронизацию отдельным OpenSpec change на основе реальных требований.

## Migration Plan

1. Зафиксировать решение отдельным ADR-0004 до переноса файлов.
2. Ввести port, use cases и Zustand store с тестами, затем перемещать доменную логику, Dexie-адаптер и presentation малыми сохраняющими поведение шагами.
3. До удаления старых файлов подтвердить, что существующая база version 1 открывается без миграции и сценарии доски проходят без изменения данных.
4. Выпустить change как обычный совместимый рефакторинг. Если регрессия обнаружена до изменения IndexedDB schema, откатить код на предыдущий bundle; пользовательские данные остаются совместимы.
