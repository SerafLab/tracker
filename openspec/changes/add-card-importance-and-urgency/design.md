# Design

## Context

Мотивация и границы поведения описаны в [proposal.md](proposal.md), проверяемые требования — в [specs/project-boards/spec.md](specs/project-boards/spec.md). Термины важности и срочности уже определены в `GLOSSARY.md`.

В текущем `Card` есть `id`, `statusId`, `name`, `position`. `DexieProjectBoardRepository.board()` читает карточки по `position`; создание добавляет их в конец статуса, а перенос атомарно добавляет в конец назначения и уплотняет источник. База объявляет только версию 1. Создание и переименование используют общий `NameDialog`; store возвращает результат записи, но обработчики создания и переименования в `ProjectBoardApp` превращают его в `Promise<void>`, поэтому существующая форма закрывается даже при неудачной записи. Новая форма карточки должна получать результат явно.

Проверки уже распределены между `domain.test.ts`, `use-cases.test.ts`, тестами IndexedDB и store, `src/app.test.tsx` и `e2e/card-moves.spec.ts`. Тесты устаревшего соединения в `database.test.ts` и `app.test.tsx` пока используют фиксированную версию 2 как более новую. Проверка архитектуры требует сохранять границы feature. Активные изменения удаления и панели приложения ещё не реализованы.

## Goals / Non-Goals

**Goals:**

- Один постоянный порядок карточек, одинаково читаемый repository, UI и будущим удалением.
- Атомарное сохранение редактируемых полей и порядка, включая перенос и обновление существующих данных.
- Явный результат сохранения для формы и сохранение её черновика при отказе записи.
- Повторное использование Dexie, существующего диалога и i18n без новых зависимостей.

**Non-Goals:**

- Второй независимый порядок в UI, отдельная таблица групп или журнал изменений важности и срочности.
- Поддержка старого API `renameCard` и чтение старых записей через необязательные признаки после миграции.
- Переработка форм проектов и статусов, глобальная переделка фокуса всех диалогов или включение соседних OpenSpec changes в эту функцию.

## Decisions

### 1. Два обязательных поля и одно редактирование карточки

Расширить `Card` обязательными `important: boolean` и `urgent: boolean`. Передавать в создание и редактирование объект `{ name, important, urgent }`; новые формы задают `false/false`, существующие заполняются данными карточки. Use cases сохраняют существующую очистку пробелов и проверку непустого названия. Заменить `renameCard` на `updateCard` во всём вертикальном срезе repository → use cases → store → presentation. Поле `statusId` меняет только операция переноса; `position` остаётся внутренней ответственностью repository.

Отдельные команды `setImportant` и `setUrgent` сделали бы сохранение формы частичным и породили несколько перестановок за одно действие. Необязательные поля и постоянное `undefined ?? false` скрывали бы незавершённую миграцию. Старые вызовы и тестовые фикстуры обновляются вместе с контрактом.

### 2. `position` — итоговый порядок всего статуса

Сохранить `position` как плотную последовательность `0…n-1` внутри статуса. Она уже отражает последовательность групп `(true,true)`, `(true,false)`, `(false,true)`, `(false,false)` и стабильный порядок внутри них. UI продолжает отображать массив repository без своей сортировки. `board()` по-прежнему читает `position`; никакой конкурирующий порядок по имени, ID или времени не вводится.

Добавить небольшой чистый доменный помощник: из списка по `position` исключить целевую карточку, найти место после последней карточки той же группы (или перед первой менее приоритетной группой, если текущая пуста), вставить карточку и перенумеровать список. Сравнивать сначала `important`, затем `urgent`, оба по убыванию. Существующий помощник перемещения статусов не менять.

| Операция | Действие с порядком |
| --- | --- |
| Создание | Вставить новую карточку в конец её группы целевого статуса |
| Изменение одного или обоих признаков | Удалить карточку с прежнего места и вставить в конец новой группы |
| Только название или исходная комбинация после переключений до сохранения | Обновить поля без смены позиции |
| Перенос в другой статус | Сохранить признаки, уплотнить источник, вставить в конец группы назначения |
| Перенос в текущий статус | Ничего не менять; UI такой выбор не предлагает |

В repository сравнивать отправленные признаки с последними сохранёнными значениями внутри транзакции, а не с промежуточным состоянием переключателей. Отдельные последующие изменения туда и обратно каждый раз добавляют карточку в конец выбранной группы. Относительный порядок всех остальных карточек сохраняется.

Альтернатива — хранить `position` только как порядок прибытия и сортировать по признакам при чтении. Она создаёт два смысла порядка и усложняет согласование с уплотнением позиций при удалении. Отдельные позиции внутри групп, временные метки и индексы по булевым признакам не нужны: текущая загрузка уже читает все карточки статуса.

### 3. Транзакция включает проверку, изменение и перенумерацию

Создание, редактирование и перенос выполняют все чтения актуальных данных и записи в одной `rw`-транзакции Dexie. Создание проверяет существование статуса и включает `statuses` и `cards`, чтобы согласоваться с удалением пустого статуса. Перенос сохраняет текущую проверку принадлежности обоих статусов одному проекту и включает те же таблицы. Редактирование читает карточку, сравнивает признаки и при их изменении пишет весь изменённый порядок статуса в одной транзакции `cards`. Отсутствующая карточка при редактировании не должна давать ложный успех.

Обновления полей и перенумерация используют целые карточки с сохранением всех их полей. При сбое Dexie откатывает и поля, и порядок; отложенного второго прохода вне транзакции нет. Последовательные транзакции записи по общим таблицам не позволяют параллельным созданиям назначить одинаковое место в группе.

Альтернатива — сначала записать признаки, затем отсортировать UI или дописать позиции. Она допускает частичное состояние после ошибки и различия после перезагрузки.

### 4. Форма карточки поверх существующего диалога

Выделить специализированную форму/диалог карточки в presentation, используя `ActionDialog` для оболочки. `NameDialog` остаётся для проектов и статусов. В карточке действие «Переименовать» заменить на «Редактировать» / «Edit» и показывать название вместе с двумя подписанными двоичными переключателями. Использовать нативные checkbox с доступными именами и оформлением переключателей; не добавлять библиотеку для двух полей. Метки «Важная» / «Срочная» и «Important» / «Urgent» — текстовые, только для включённых признаков, с переносом строк на узком экране.

Передавать `Promise<boolean>` из операций store через обработчики `ProjectBoardApp` до формы. Закрывать и очищать форму только после успешного сохранения; при отказе оставлять поля, показывать локализованную ошибку внутри диалога и разрешать повторную попытку. Пока запрос выполняется, блокировать повторную отправку и редактирование полей. `onMutationSaved` вызывается только после подтверждённой записи. Store перечитывает доску после записи, поэтому метки и порядок обновляются без перезагрузки; при отказе самой записи доска остаётся прежней. Если запись прошла, но повторное чтение недоступно, использовать существующее состояние ошибки хранилища, не показывая устаревшую доску как актуальную.

Ключ React остаётся `card.id`, поэтому перестановка в том же статусе не создаёт новую карточку и не теряет состояние диалога. На открытии фокус получает название; после закрытия редактирования фокус возвращается на кнопку меню карточки, даже если она сменила место. Для создания — на кнопку создания соответствующего статуса. Не полагаться на удалённый пункт меню как на сохранённый opener. Для переноса оставить существующий механизм фокуса в `ProjectBoardView`, включая `preventScroll`, недоступные граничные стрелки и запасной фокус на меню.

Альтернатива — расширять `NameForm` множеством условных полей для всех сущностей. Это смешивает форму имени с состоянием карточки и увеличивает пересечения с другими изменениями.

### 5. Миграция обязательна, индексы остаются прежними

Объявить версию 2 Dexie с прежними таблицами и индексами и транзакционным `upgrade`, который добавляет существующим карточкам `important: false`, `urgent: false`. Сохранить их `position` без перенумерации: все попадают в одну группу и прежний порядок остаётся действительным. Не менять ID, названия, связи, проекты, статусы и workspace preference. Новые базы сразу создают записи через актуальную модель.

Миграцию проверять на настоящей базе v1, созданной отдельным Dexie с прежней схемой, закрытой до открытия новой версии. Добавление записи без полей в уже обновлённую базу не является тестом миграции. Проверить несколько проектов, статусов и неалфавитный порядок карточек, повторное открытие, сохранение других таблиц и откат при ошибке upgrade. Тестам `versionchange` нужна версия строго выше актуальной (после изменения — 3), иначе они перестанут моделировать устаревшее соединение. Существующая блокировка изменений в старой вкладке и сообщение о перезапуске сохраняются.

Альтернатива — подставлять значения только при чтении. Она оставляет смешанный формат хранения и не гарантирует обязательные поля во всех путях записи.

## Integration Considerations

- `delete-cards-and-statuses` планирует уплотнять `position` оставшихся карточек. Общий контракт: читать их в сохранённом порядке и перенумеровывать, не сортируя по имени/ID и не удаляя признаки. Тогда удаление сохраняет и группы, и порядок внутри них. Пересечения: repository, его интерфейс, use cases, store, меню карточки/статуса, переводы и тестовые фикстуры. Проверить цепочку «изменить признаки → удалить соседнюю карточку → создать/перенести карточку → перезагрузить». Создание в транзакции с `statuses` согласуется с проверкой пустоты при удалении статуса. Функции не следует объявлять независимыми на уровне этих контрактов.
- `unify-app-bar` меняет `ActionDialog`, место селектора языка и фокус модального окна. Новый диалог карточки использует итоговую общую оболочку и не добавляет собственного селектора. Если реализуется только эта функция, сохраняется текущая оболочка; при совместной интеграции селектор остаётся только в панели, недоступной за модальным окном. Тесты ru/en не должны требовать переключения языка внутри диалога. Пересечения: `project-board-view`, `project-board-app`, CSS, i18n и общие UI/e2e фикстуры.
- Эта функция не зависит от реализации удаления или панели для самостоятельной поставки. При будущем запросе пакета основной чат сначала согласует общий контракт порядка и общую оболочку диалога, определит единственного владельца общей правки и порядок зависимостей, затем выделит отдельные ветки и рабочие деревья. Общую оболочку из `unify-app-bar` следует интегрировать перед адаптацией новой формы; контракт порядка этого изменения — перед окончательной проверкой удаления. Сейчас создаются только артефакты данной функции, соседние changes не меняются.
- `interface-language` уже требует перевода всего текста приложения; новых языковых правил нет, поэтому отдельная дельта для этой capability не нужна. Backup не реализован и не входит в этот план. Отдельный ADR не нужен: выбранное представление порядка и форма обратимы и локальны для feature.

## Risks / Trade-offs

- [Перезапись списка имеет линейную стоимость по размеру статуса] → использовать одну пакетную запись в транзакции; это согласуется с существующей полной загрузкой статуса и уплотнением после переноса, без нового слоя индексации.
- [Сортировка только по признакам переставит карточку внутри группы непредсказуемо] → вставлять изменённую карточку явно в конец новой группы, проверять все комбинации и неизменность порядка остальных.
- [Форма закроется после неудачной записи из-за прежнего `Promise<void>`] → провести булев результат через весь срез и проверить удержание черновика, ошибку и повторную попытку.
- [Перестановка или закрытие меню потеряет клавиатурный фокус] → привязать возврат к существующей кнопке карточки по ID и проверить редактирование и перенос в браузере на 320 и 1280 px.
- [Миграция нарушит тесты устаревшей вкладки или подменит настоящий upgrade тестом фикстуры] → отдельно тестировать v1→v2 и v2→более новая версия, включая защиту от записи старой вкладкой.
- [Соседнее изменение потеряет поля при пересборке карточки или вернёт конец всего статуса] → согласовать контракт до совместной реализации и проверить комбинированные операции после интеграции.

## Migration Plan

1. Обновить модель, единый контракт редактирования и доменный порядок; затем операции repository и версию 2 с upgrade. Основную спецификацию не синхронизировать в ходе реализации без отдельного запроса.
2. Подключить store, форму и метки; перевести новые подписи, адаптировать фикстуры и проверки устаревшего соединения.
3. Выполнить тесты реального обновления v1→v2, атомарности и порядка; UI/e2e сценарии ошибок, клавиатуры и двух языков; затем `npm run check` и строгую валидацию OpenSpec.
4. На доставке открытие актуальной версии приложения выполняет upgrade автоматически, а старое соединение закрывается через существующий `versionchange`. При сбое upgrade исходные данные сохраняются, приложение показывает ошибку открытия хранилища.
5. Откат выпуска после успешной миграции требует исправляющей версии приложения, читающей текущую схему, либо следующей прямой миграции. Понижать версию базы, удалять её или возвращать приложение v1 поверх v2 не планируется. Старая модель/API не поддерживается; данные сохраняются при исправлении вперёд.

Планирование не означает доставку: реализация, коммит, отправка, PR и архивация выполняются только по соответствующим последующим запросам пользователя.
